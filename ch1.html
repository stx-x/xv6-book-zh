第 1 章　操作系统组织 ​

操作系统的一项关键需求是同时支持多项活动。例如，使用 第 0 章 介绍的系统调用接口，进程可以用 fork 启动新进程。操作系统必须在这些进程之间对计算机的资源进行分时。例如，即使进程数量多于硬件处理器的数量，操作系统也必须确保所有进程都能取得进展。操作系统还必须安排进程之间的隔离。也就是说，如果一个进程有缺陷并失败，它不应影响那些不依赖该失败进程的进程。然而，完全隔离又太强了，因为进程之间应当能够交互；管道就是一个例子。因此，操作系统必须满足三项要求：多路复用、隔离和交互。

本章概述操作系统如何组织起来以满足这三项要求。实现方式有很多，但本文关注以宏内核为中心的主流设计，许多 Unix 操作系统都采用这种设计。本章通过追踪 xv6 启动时第一个进程的创建过程来介绍 xv6 的设计。在此过程中，本文会展示 xv6 提供的所有主要抽象的实现、它们如何相互作用，以及多路复用、隔离和交互这三项要求如何得到满足。xv6 的大部分代码都避免为第一个进程做特殊处理，而是复用 xv6 为常规运行必须提供的代码。后续各章将更详细地探讨每一种抽象。

xv6 运行在 PC 平台的 Intel 80386 或更高（“x86”）处理器上，它的许多底层功能（例如进程的实现）是 x86 特有的。本书假定读者已在某种体系结构上做过一些机器级编程，并会在需要时介绍 x86 特有的概念。附录简要概述了 PC 平台。

抽象物理资源 ​

遇到一个操作系统时，人们可能首先会问：为什么要有它？也就是说，人们可以把 图 0-2 中的系统调用实现为一个库，让应用程序链接它。在这种方案中，每个应用程序甚至可以拥有为自己需求量身定制的库。应用程序可以直接与硬件资源交互，并以对应用程序最有利的方式使用这些资源（例如获得高而可预测的性能）。一些面向嵌入式设备或实时系统的操作系统就是这样组织的。

这种库方式的缺点在于，如果有多个应用程序在运行，它们必须行为良好。例如，每个应用程序都必须定期让出处理器，以便其他应用程序运行。如果所有应用程序互相信任且没有缺陷，这种协作式分时方案也许可行。更常见的情况是应用程序互不信任且有缺陷，因此人们往往希望获得比协作式方案更强的隔离。

要实现强隔离，有帮助的做法是禁止应用程序直接访问敏感的硬件资源，转而把资源抽象为服务。例如，应用程序只通过 open、read、write 和 close 系统调用与文件系统交互，而不是读写原始磁盘扇区。这为应用程序提供了路径名的便利，也使操作系统（作为接口的实现者）能够管理磁盘。

类似地，Unix 在进程之间透明地切换硬件处理器，必要时保存和恢复寄存器状态，使应用程序无需感知分时。这种透明性使操作系统即使在某些应用程序陷入无限循环时也能共享处理器。

再举一个例子，Unix 进程使用 exec 构建其内存映像，而不是直接与物理内存交互。这使操作系统可以决定把进程放在内存的什么位置；如果内存紧张，操作系统甚至可以把进程的部分数据存到磁盘上。Exec 还为用户提供了用文件系统存储可执行程序映像的便利。

Unix 进程之间的许多交互形式都通过文件描述符进行。文件描述符不仅抽象掉了许多细节（例如管道或文件中的数据存放在哪里），它们的定义方式还简化了交互。例如，如果管道中的一个应用程序失败，内核会为管道中的下一个进程产生文件结束。

如你所见，图 0-2 中的系统调用接口经过精心设计，既为程序员提供便利，又使强隔离成为可能。Unix 接口并不是抽象资源的唯一方式，但它已被证明是一种非常好的方式。

用户模式、内核模式与系统调用 ​

强隔离要求应用程序与操作系统之间有一条硬边界。如果应用程序犯了错误，我们不希望操作系统失败，也不希望其他应用程序失败。相反，操作系统应当能够清理失败的应用程序并继续运行其他应用程序。要实现强隔离，操作系统必须安排应用程序不能修改（甚至不能读取）操作系统的数据结构和指令，并且应用程序不能访问其他进程的内存。

处理器为强隔离提供硬件支持。例如，x86 处理器与许多其他处理器一样，有两种执行指令的模式：内核模式和用户模式。在内核模式下，处理器被允许执行特权指令。例如，读写磁盘（或任何其他 I/O 设备）涉及特权指令。如果用户模式下的应用程序试图执行特权指令，处理器不会执行该指令，而是切换到内核模式，以便内核模式下的软件清理该应用程序，因为它做了不该做的事。第 0 章 中的 图 0-1 说明了这种组织方式。应用程序只能执行用户模式指令（例如加法等），称为运行在用户空间；而内核模式下的软件还可以执行特权指令，称为运行在内核空间。运行在内核空间（或内核模式）的软件称为内核。

想要读写磁盘文件的应用程序必须转入内核才能做到，因为应用程序本身不能执行 I/O 指令。处理器提供了一条特殊指令，把处理器从用户模式切换到内核模式，并在内核指定的入口点进入内核。（x86 处理器为此提供了 int 指令。）处理器切换到内核模式后，内核就可以验证系统调用的参数，判定是否允许应用程序执行所请求的操作，然后拒绝或执行它。内核设定进入内核模式的入口点，这一点很重要；如果应用程序能够决定内核入口点，恶意应用程序就可以从一个跳过参数验证等步骤的位置进入内核。

内核组织 ​

一个关键的设计问题是：操作系统的哪一部分应当运行在内核模式下。一种可能是整个操作系统都驻留在内核中，因而所有系统调用的实现都运行在内核模式下。这种组织方式称为宏内核。

在这种组织方式中，整个操作系统都以完整的硬件特权运行。这种组织方式很方便，因为操作系统设计者不必决定操作系统的哪一部分不需要完整的硬件特权。此外，操作系统的不同部分很容易协作。例如，操作系统可以有一个缓冲区缓存，同时供文件系统和虚拟内存系统共享。

宏内核组织方式的缺点是，操作系统不同部分之间的接口往往很复杂（我们将在本书余下部分看到这一点），因此操作系统开发者很容易犯错。在宏内核中，错误是致命的，因为内核模式下的错误往往会导致内核失败。如果内核失败，计算机就停止工作，因而所有应用程序也都失败。计算机必须重启才能再次启动。

为了降低内核中出错的风险，操作系统设计者可以尽量减少运行在内核模式下的操作系统代码量，而把操作系统的主体放在用户模式下执行。这种内核组织方式称为微内核。

图 1-1 说明了这种微内核设计。图中，文件系统作为用户级进程运行。作为进程运行的操作系统服务称为服务器。为了让应用程序能够与文件服务器交互，内核提供了一种进程间通信机制，用于把一个用户模式进程的消息发送给另一个用户模式进程。例如，如果像 shell 这样的应用程序想要读写文件，它就向文件服务器发送一条消息，并等待响应。

在微内核中，内核接口由少量底层函数组成，用于启动应用程序、发送消息、访问设备硬件等。这种组织方式使内核可以相对简单，因为操作系统的大部分都驻留在用户级服务器中。

xv6 按照大多数 Unix 操作系统的做法，实现为宏内核。因此，在 xv6 中，内核接口就对应操作系统接口，内核实现了完整的操作系统。由于 xv6 提供的服务不多，它的内核比一些微内核还要小。

进程概述 ​

xv6 中（与其他 Unix 操作系统一样）的隔离单位是进程。进程抽象防止一个进程破坏或窥探另一个进程的内存、CPU、文件描述符等。它还防止进程破坏内核本身，使进程无法颠覆内核的隔离机制。内核必须谨慎地实现进程抽象，因为有缺陷或恶意的应用程序可能诱使内核或硬件做出坏事（例如绕过强制的隔离）。内核用来实现进程的机制包括用户/内核模式标志、地址空间以及线程的时间片轮转。

为了帮助实施隔离，进程抽象为程序提供一种幻觉：它拥有自己私有的机器。进程为程序提供一个看似私有的内存系统，即地址空间，其他进程不能读写它。进程还为程序提供一个看似属于自己的 CPU，用来执行程序的指令。

xv6 使用页表（由硬件实现）为每个进程提供自己的地址空间。x86 页表把虚拟地址（x86 指令操作的地址）转换（或“映射”）为物理地址（处理器芯片发送给主存的地址）。

xv6 为每个进程维护一张单独的页表，用以定义该进程的地址空间。如 图 1-2 所示，地址空间包含从虚拟地址零开始的进程用户内存。指令排在最前面，接着是全局变量，然后是栈，最后是一块“堆”区域（供 malloc 使用），进程可以按需扩展它。

每个进程的地址空间既映射用户程序的内存，也映射内核的指令和数据。当进程调用系统调用时，系统调用在该进程地址空间的内核映射中执行。这样安排是为了让内核的系统调用代码能够直接引用用户内存。为了给用户内存留出充足的空间，xv6 的地址空间把内核映射在高地址处，起始于 0x80100000。

xv6 内核为每个进程维护许多状态，并把它们汇集到一个 struct proc (2337) 中。进程最重要的内核状态是它的页表、内核栈和运行状态。我们将用 p->xxx 这种写法来引用 proc 结构中的成员。

每个进程都有一个执行线程（简称线程），执行该进程的指令。线程可以被挂起，稍后再恢复。为了在进程之间透明地切换，内核挂起当前正在运行的线程，并恢复另一个进程的线程。线程的许多状态（局部变量、函数调用的返回地址）保存在线程的栈上。每个进程有两个栈：用户栈和内核栈（p->kstack）。当进程执行用户指令时，只有用户栈在使用，内核栈是空的。当进程进入内核（因系统调用或中断）时，内核代码在该进程的内核栈上执行；进程处于内核中时，其用户栈仍然保存着数据，但并未被积极使用。进程的线程在积极使用用户栈和内核栈之间交替。内核栈是独立的（并且对用户代码受保护），这样即使进程破坏了自己的用户栈，内核仍能执行。

当进程发起系统调用时，处理器切换到内核栈，提升硬件特权级，并开始执行实现该系统调用的内核指令。系统调用完成后，内核返回用户空间：硬件降低特权级，切回用户栈，并在系统调用指令之后恢复执行用户指令。进程的线程可以在内核中“阻塞”以等待 I/O，并在 I/O 完成后从离开的地方继续。

p->state 指示进程是已分配、可运行、正在运行、等待 I/O，还是正在退出。

p->pgdir 保存进程的页表，格式是 x86 硬件所期望的。xv6 在执行某个进程时，会让分页硬件使用该进程的 p->pgdir。进程的页表同时也是记录：哪些物理页被分配用来存放该进程的内存。

代码：第一个地址空间 ​

为了让 xv6 的组织方式更具体，我们来看内核如何创建第一个地址空间（为它自己），内核如何创建并启动第一个进程，以及该进程如何执行第一次系统调用。通过追踪这些操作，我们能够详细看到 xv6 如何为进程提供强隔离。提供强隔离的第一步，是让内核运行在自己的地址空间中。

PC 加电时会自我初始化，然后从磁盘把一个引导加载器装入内存并执行它。附录会解释其中的细节。xv6 的引导加载器从磁盘加载 xv6 内核，并从 entry (1044) 开始执行它。内核启动时 x86 分页硬件尚未启用；虚拟地址直接映射到物理地址。

引导加载器把 xv6 内核装入物理地址 0x100000 处的内存。它之所以不把内核装入内核期望找到其指令和数据的位置，是因为小型机器上如此高的地址处可能根本没有物理内存。它之所以把内核放在 0x100000 而不是 0x0，是因为地址范围 0xa0000:0x100000 包含 I/O 设备。

为了让内核的其余部分得以运行，entry 建立了一张页表，把从 0x80000000（称为 KERNBASE (0207)）开始的虚拟地址映射到从 0x0 开始的物理地址（见 图 1-2）。建立两段映射到同一物理内存范围的虚拟地址，是页表的一种常见用法，我们还会看到更多类似的例子。

这张入口页表定义在 main.c 中。我们将在 第 2 章 详细讨论页表的细节，但简要地说，第 0 项把虚拟地址 0:0x400000 映射到物理地址 0:0x400000。只要 entry 还在低地址处执行，这个映射就是必需的，但最终会被移除。

第 512 项把虚拟地址 KERNBASE:KERNBASE+0x400000 映射到物理地址 0:0x400000。内核在 entry 完成后将使用这一项；它把内核期望找到其指令和数据的高虚拟地址，映射到引导加载器装入它们时的低物理地址。这个映射把内核的指令和数据限制在 4 MB 以内。

回到 entry，它把 entrypgdir 的物理地址装入控制寄存器 cr3。cr3 中的值必须是物理地址。让 cr3 保存 entrypgdir 的虚拟地址是说不通的，因为分页硬件还不知道如何转换虚拟地址；它还没有页表。符号 entrypgdir 指的是高内存中的一个地址，宏 V2P_WO 减去 KERNBASE 以求出物理地址。为了启用分页硬件，xv6 在控制寄存器 cr0 中设置 CR0_PG 标志。

启用分页之后，处理器仍在低地址处执行指令，这之所以可行，是因为 entrypgdir 映射了低地址。如果 xv6 从 entrypgdir 中去掉第 0 项，那么在试图执行启用分页那条指令之后的下一条指令时，计算机就会崩溃。

现在 entry 需要转入内核的 C 代码，并在高内存中运行它。首先，它让栈指针 esp 指向用作栈的内存 (1058)。所有符号都具有高地址，包括 stack，因此即使低地址映射被移除，栈仍然有效。最后，entry 跳转到 main，它也是一个高地址。这里需要间接跳转，因为否则汇编器会生成 PC 相对的直接跳转，那将执行低内存版本的 main。Main 不能返回，因为栈上没有返回 PC。现在内核正在高地址处、在函数 main (1217) 中运行。

代码：创建第一个进程 ​

现在我们来看内核如何创建用户级进程，并确保它们被强隔离。

main (1217) 初始化若干设备和子系统之后，通过调用 userinit (2520) 创建第一个进程。Userinit 的第一个动作是调用 allocproc。allocproc (2473) 的任务是在进程表中分配一个槽位（一个 struct proc），并初始化进程状态中内核线程执行所需的部分。Allocproc 会为每个新进程调用，而 userinit 只为第一个进程调用。Allocproc 扫描 proc 表，寻找状态为 UNUSED 的槽位 (2480-2482)。找到未使用的槽位后，allocproc 把状态设为 EMBRYO 以标记它已被使用，并给该进程分配一个唯一的 pid (2469-2489)。接下来，它尝试为该进程的内核线程分配一个内核栈。如果内存分配失败，allocproc 把状态改回 UNUSED 并返回零以示失败。

现在 allocproc 必须建立新进程的内核栈。allocproc 的写法使它既能用于 fork，也能用于创建第一个进程。allocproc 为新进程准备一个特殊构造的内核栈和一组内核寄存器，使新进程首次运行时“返回”到用户空间。所准备的内核栈的布局如 图 1-4 所示。allocproc 完成其中一部分工作：设置返回的程序计数器值，使新进程的内核线程先执行 forkret，然后执行 trapret (2507-2512)。内核线程将使用从 p->context 复制的寄存器内容开始执行。因此，把 p->context->eip 设为 forkret 将使内核线程从 forkret (2853) 的开头开始执行。这个函数将返回到栈底处的地址。上下文切换代码把栈指针设置为刚好越过 p->context 末尾的位置。allocproc 把 p->context 放在栈上，并在它上面放一个指向 trapret 的指针；forkret 就将返回到那里。trapret 从内核栈顶存储的值恢复用户寄存器，并跳入进程 (3324)。这一设置对普通的 fork 和创建第一个进程是相同的，只不过在后一种情况下，进程将从用户空间的地址零开始执行，而不是从 fork 返回处开始。

正如我们将在 第 3 章 看到的，控制从用户软件转移到内核的方式是通过中断机制，系统调用、中断和异常都使用它。每当进程运行期间控制转入内核时，硬件和 xv6 的陷阱入口代码都会把用户寄存器保存在该进程的内核栈上。userinit 在新栈顶写入的值，看起来就像进程通过中断进入内核时栈上会有的值 (2533-2539)，这样从内核返回进程用户代码的常规代码就能正常工作。这些值构成一个 struct trapframe，用来保存用户寄存器。现在，新进程的内核栈已完全准备好，如 图 1-4 所示。

第一个进程将要执行一个小程序（initcode.S；(8400)）。该进程需要物理内存来存放这个程序，程序需要被复制到那块内存，进程还需要一张把用户空间地址映射到那块内存的页表。

userinit 调用 setupkvm (1818) 为进程创建页表，起初只映射内核使用的内存。我们将在 第 2 章 详细研究这个函数，但概括地说，setupkvm 和 userinit 创建的地址空间如 图 1-2 所示。

第一个进程用户空间内存的初始内容是 initcode.S 的编译产物；作为内核构建过程的一部分，链接器把该二进制嵌入内核，并定义两个特殊符号 _binary_initcode_start 和 _binary_initcode_size，指明该二进制的位置和大小。Userinit 调用 inituvm 把该二进制复制到新进程的内存中，inituvm 分配一页物理内存，把虚拟地址零映射到该内存，并把二进制复制到这一页 (1886)。

然后 userinit 用初始用户模式状态设置陷阱帧 (0602)：cs 寄存器包含 SEG_UCODE 段的段选择子，运行在特权级 DPL_USER（即用户模式而非内核模式）；类似地，ds、es 和 ss 使用 SEG_UDATA，特权级为 DPL_USER。eflags 的 FL_IF 位被置位，以允许硬件中断；我们将在 第 3 章 重新审视这一点。

栈指针 esp 被设为进程最大的有效虚拟地址 p->sz。指令指针被设为 initcode 的入口点，即地址 0。

函数 userinit 把 p->name 设为 initcode，主要是为了调试。设置 p->cwd 则设定进程的当前工作目录；我们将在 第 6 章 详细研究 namei。

进程初始化完成后，userinit 把 p->state 设为 RUNNABLE，把它标记为可调度。

代码：运行第一个进程 ​

现在第一个进程的状态已经准备好，是时候运行它了。main 调用 userinit 之后，mpmain 调用 scheduler 开始运行进程 (1257)。Scheduler (2758) 寻找 p->state 为 RUNNABLE 的进程，只有一个：initproc。它把每 CPU 变量 proc 设为找到的进程，并调用 switchuvm 告诉硬件开始使用目标进程的页表 (1879)。在内核中执行时切换页表之所以可行，是因为 setupkvm 使所有进程的页表对内核代码和数据具有相同的映射。switchuvm 还建立一个任务状态段 SEG_TSS，指示硬件在该进程的内核栈上执行系统调用和中断。我们将在 第 3 章 重新审视任务状态段。

scheduler 现在把 p->state 设为 RUNNING，并调用 swtch 执行到目标进程内核线程的上下文切换。swtch 首先保存当前寄存器。当前上下文不是进程，而是一个特殊的每 CPU 调度器上下文，因此 scheduler 让 swtch 把当前硬件寄存器保存到每 CPU 存储（cpu->scheduler）中，而不是保存到任何进程的内核线程上下文中。然后 swtch 把目标内核线程（p->context）保存的寄存器装入 x86 硬件寄存器，包括栈指针和指令指针。我们将在 第 5 章 更详细地研究 swtch。最后的 ret 指令从栈上弹出目标进程的 eip，完成上下文切换。现在处理器正运行在进程 p 的内核栈上。

Allocproc 先前已把 initproc 的 p->context->eip 设为 forkret，因此 ret 开始执行 forkret。在第一次调用时（也就是这一次），forkret (2853) 运行一些初始化函数，这些函数不能从 main 中运行，因为它们必须在一个拥有自己内核栈的常规进程上下文中运行。然后 forkret 返回。Allocproc 已经安排好：p->context 被弹出后栈顶的字是 trapret，所以现在 trapret 开始执行，esp 被设为 p->tf。Trapret (3324) 使用 pop 指令从陷阱帧 (0602) 恢复寄存器，正如 swtch 对内核上下文所做的那样：popal 恢复通用寄存器，然后 popl 指令恢复 gs、fs、es 和 ds。addl 跳过 trapno 和 errcode 这两个字段。最后，iret 指令从栈上弹出 cs、eip、flags、esp 和 ss。陷阱帧的内容已被转移到 CPU 状态，因此处理器在陷阱帧中指定的 eip 处继续执行。对 initproc 来说，那就是虚拟地址零，即 initcode.S 的第一条指令。

此时，eip 的值为零，esp 的值为 4096。它们是进程地址空间中的虚拟地址。处理器的分页硬件把它们转换为物理地址。allocuvm 已经建立了进程的页表，使虚拟地址零指向为该进程分配的物理内存，并设置了一个标志（PTE_U），告诉分页硬件允许用户代码访问该内存。userinit (2533) 把 cs 的低位设置为在 CPL=3 下运行进程的用户代码，这意味着用户代码只能使用设置了 PTE_U 的页，并且不能修改 cr3 等敏感硬件寄存器。因此，进程被限制为只能使用自己的内存。

第一次系统调用：exec ​

既然我们已经看到内核如何为进程提供强隔离，接下来看看用户级进程如何重新进入内核，以请求它自己无法完成的服务。

initcode.S 的第一个动作是调用 exec 系统调用。正如我们在 第 0 章 看到的，exec 用新程序替换当前进程的内存和寄存器，但保留文件描述符、进程 ID 和父进程不变。

Initcode.S (8409) 首先在栈上压入三个值——$argv、$init 和 $0——然后设置 eax 为 SYS_exec 并执行 int T_SYSCALL：它在请求内核运行 exec 系统调用。如果一切顺利，exec 永不返回：它开始运行由 $init 命名的程序，$init 是指向以 NUL 结尾的字符串 /init 的指针 (8422-8424)。另一个参数是命令行参数数组 argv；数组末尾的零标记它的结束。如果 exec 失败并返回，initcode 就循环调用 exit 系统调用，而后者绝对不应返回 (8416-8420)。

这段代码手工构造第一次系统调用，使它看起来像一次普通的系统调用，我们将在 第 3 章 看到这一点。和前面一样，这种设置避免为第一个进程（这里是它的第一次系统调用）做特殊处理，而是复用 xv6 为常规运行必须提供的代码。

第 2 章 将详细讨论 exec 的实现，但概括地说，它用从文件系统加载的 /init 二进制替换 initcode。现在 initcode (8400) 的使命完成，进程将改为运行 /init。Init (8510) 在需要时创建一个新的控制台设备文件，然后把它作为文件描述符 0、1、2 打开。接着它进入循环：启动一个控制台 shell，处理孤儿僵尸进程直到 shell 退出，然后重复。系统就此启动。

现实世界 ​

在现实世界中，宏内核和微内核都能见到。许多 Unix 内核是宏内核。例如，Linux 有一个宏内核，尽管某些操作系统功能以用户级服务器运行（例如窗口系统）。L4、Minix、QNX 等内核组织为带服务器的微内核，并在嵌入式环境中得到了广泛部署。

大多数操作系统都采用了进程概念，大多数进程看起来与 xv6 的进程相似。真实操作系统会用显式的空闲链表在常数时间内找到空闲的 proc 结构，而不是像 allocproc 那样线性搜索；xv6 为了简单而使用线性扫描（这是众多简化中的第一个）。
