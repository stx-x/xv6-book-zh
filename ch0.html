第 0 章　操作系统接口 ​

操作系统的工作是把一台计算机在多个程序之间共享，并提供一组比裸硬件所支持的更有用的服务。操作系统管理和抽象底层硬件，因此，举例来说，文字处理器不必关心使用的是哪一类磁盘硬件。它还在多个程序之间共享硬件，使它们同时（或看似同时）运行。最后，操作系统为程序之间的交互提供受控的方式，使它们能够共享数据或协同工作。

操作系统通过接口向用户程序提供服务。设计一个好的接口并不容易。一方面，我们希望接口简单而狭窄，因为这样更容易把实现做对。另一方面，我们又可能忍不住向应用程序提供许多复杂的功能。化解这一张力的诀窍在于，设计只依赖少数机制的接口，这些机制可以组合起来提供极大的通用性。

本书以单个操作系统作为具体例子来说明操作系统概念。这个操作系统名为 xv6，它提供了 Ken Thompson 和 Dennis Ritchie 的 Unix 操作系统所引入的基本接口，同时模仿了 Unix 的内部设计。Unix 提供的接口很窄，其机制组合良好，带来了惊人的通用性。这一接口如此成功，以至于现代操作系统——BSD、Linux、Mac OS X、Solaris，甚至在较小程度上包括 Microsoft Windows——都拥有类 Unix 的接口。理解 xv6 是理解这些系统以及许多其他系统的良好起点。

如 图 0-1 所示，xv6 采用传统的内核形式：内核是一个特殊程序，为正在运行的程序提供服务。每个正在运行的程序称为进程，它拥有包含指令、数据和栈的内存。指令实现程序的计算。数据是计算所作用的变量。栈组织程序的过程调用。

当一个进程需要调用内核服务时，它会调用操作系统接口中的一个过程。这样的过程称为系统调用。系统调用进入内核；内核执行服务并返回。因此，进程在用户空间和内核空间中交替执行。

内核利用 CPU 的硬件保护机制，确保每个在用户空间执行的进程只能访问自己的内存。内核在实现这些保护所需的硬件特权级下执行；用户程序则在没有这些特权的情况下执行。当用户程序发起系统调用时，硬件提升特权级，并开始执行内核中预先安排好的函数。

内核所提供的系统调用的集合，就是用户程序所看到的接口。xv6 内核提供了 Unix 内核传统上提供的服务和系统调用的一个子集。图 0-2 列出了 xv6 的全部系统调用。

本章余下部分概述 xv6 的服务——进程、内存、文件描述符、管道和文件系统——并通过代码片段以及关于 shell 如何使用这些服务的讨论来说明它们；shell 是传统类 Unix 系统的主要用户界面。shell 对系统调用的使用，说明了这些调用设计得多么精心。

shell 是一个普通程序，它从用户那里读取命令并执行它们。shell 是用户程序而非内核的一部分，这一事实说明了系统调用接口的力量：shell 并没有什么特别之处。这也意味着 shell 很容易被替换；因此，现代 Unix 系统有各种各样的 shell 可供选择，每个都有自己的用户界面和脚本功能。xv6 的 shell 是对 Unix Bourne shell 精髓的简单实现。其实现见 (8549)。

进程与内存 ​

一个 xv6 进程由用户空间内存（指令、数据和栈）以及内核私有的每进程状态组成。xv6 可以对进程进行分时：它在等待执行的进程集合之间透明地切换可用的 CPU。当一个进程没有执行时，xv6 保存它的 CPU 寄存器，并在下次运行该进程时恢复它们。内核为每个进程关联一个进程标识符，即 pid。

进程可以使用 fork 系统调用创建一个新进程。Fork 创建一个新进程，称为子进程，其内存内容与调用进程——称为父进程——完全相同。Fork 在父进程和子进程中都会返回。在父进程中，fork 返回子进程的 pid；在子进程中，它返回零。例如，考虑下面的程序片段：

int pid = fork();
if(pid > 0){
  printf("parent: child=%d\en", pid);
  pid = wait();
  printf("child %d is done\en", pid);
} else if(pid == 0){
  printf("child: exiting\en");
  exit();
} else {
  printf("fork error\en");
}

exit 系统调用使调用进程停止执行，并释放内存和打开的文件等资源。wait 系统调用返回当前进程某个已退出子进程的 pid；如果调用者没有任何子进程已经退出，wait 会等待其中一个退出。在上面的例子中，输出行

parent: child=1234
child: exiting

可能以任意顺序出现，这取决于父进程还是子进程先执行到它的 printf 调用。子进程退出后，父进程的 wait 返回，使父进程打印

parent: child 1234 is done

尽管子进程最初拥有与父进程相同的内存内容，但父进程和子进程是在不同的内存和不同的寄存器上执行的：改变其中一个中的变量不会影响另一个。例如，当 wait 的返回值被存入父进程中的 pid 时，它不会改变子进程中的变量 pid。子进程中 pid 的值仍然是零。

exec 系统调用用从文件系统中存储的文件加载的新内存映像替换调用进程的内存。该文件必须具有特定的格式，格式规定了文件的哪一部分存放指令、哪一部分是数据、从哪条指令开始执行，等等。xv6 使用 ELF 格式，第 2 章 将更详细地讨论它。当 exec 成功时，它不会返回到调用程序；取而代之的是，从文件加载的指令从 ELF 头部声明的入口点开始执行。Exec 接受两个参数：包含可执行文件的文件名，以及一个字符串参数数组。例如：

char *argv[3];
argv[0] = "echo";
argv[1] = "hello";
argv[2] = 0;
exec("/bin/echo", argv);
printf("exec error\en");

这个片段把调用程序替换为程序 /bin/echo 的一个实例，并以参数列表 echo hello 运行。大多数程序忽略第一个参数，按照惯例它是程序名。

xv6 的 shell 使用上述调用来代表用户运行程序。shell 的主体结构很简单；见 main (8701)。主循环用 getcmd 从用户那里读取一行输入。然后它调用 fork，创建 shell 进程的一个副本。父进程调用 wait，而子进程运行命令。例如，如果用户向 shell 输入了“echo hello”，那么 runcmd 就会以“echo hello”作为参数被调用。runcmd (8606) 运行实际的命令。对于“echo hello”，它会调用 exec (8626)。如果 exec 成功，那么子进程将执行 echo 的指令，而不是 runcmd 的指令。在某个时刻，echo 会调用 exit，这将使父进程从 main (8701) 中的 wait 返回。你可能会问，为什么 fork 和 exec 不合并为一个调用；我们稍后会看到，把创建进程和加载程序分成两个调用是一个巧妙的设计。

xv6 隐式地分配大部分用户空间内存：fork 分配子进程复制父进程内存所需的内存，exec 分配足以容纳可执行文件的内存。需要在运行时获得更多内存的进程（也许是为了 malloc）可以调用 sbrk(n) 把它的数据内存增加 n 字节；sbrk 返回新内存的位置。

xv6 不提供用户的概念，也不提供把一个用户与另一个用户隔离开的保护；用 Unix 的话说，所有 xv6 进程都以 root 身份运行。

I/O 与文件描述符 ​

文件描述符是一个小整数，表示一个由内核管理的对象，进程可以从中读取或向其写入。进程可以通过打开文件、目录或设备，或者创建管道，或者复制已有的描述符来获得文件描述符。为简单起见，我们常常把文件描述符所指的对象称为“文件”；文件描述符接口抽象掉了文件、管道和设备之间的差异，使它们看起来都像是字节流。

在内核内部，xv6 把文件描述符用作每进程表的下标，因此每个进程都有从零开始的私有文件描述符空间。按照惯例，进程从文件描述符 0（标准输入）读取，把输出写到文件描述符 1（标准输出），把错误消息写到文件描述符 2（标准错误）。正如我们将看到的，shell 利用这一惯例来实现 I/O 重定向和管道。shell 确保自己始终打开三个文件描述符 (8707)，它们默认是控制台的文件描述符。

read 和 write 系统调用从由文件描述符命名的打开文件中读取字节并向其写入字节。调用 read(fd, buf, n) 从文件描述符 fd 最多读取 n 字节，把它们复制到 buf，并返回读取的字节数。每个指向文件的文件描述符都有一个与之关联的偏移量。Read 从当前文件偏移量处读取数据，然后按读取的字节数推进该偏移量：后续的 read 将返回紧跟在第一次 read 所返回字节之后的字节。当没有更多字节可读时，read 返回零，以表示文件结束。

调用 write(fd, buf, n) 把 buf 中的 n 字节写到文件描述符 fd，并返回写入的字节数。只有在发生错误时，写入的字节才会少于 n。与 read 一样，write 在当前文件偏移量处写入数据，然后按写入的字节数推进该偏移量：每次 write 都从上次结束的地方继续。

下面的程序片段（它构成了 cat 的精髓）把数据从标准输入复制到标准输出。如果发生错误，它向标准错误写一条消息。

char buf[512];
int n;
for(;;){
  n = read(0, buf, sizeof buf);
  if(n == 0)
    break;
  if(n < 0){
    fprintf(2, "read error\en");
    exit();
  }
  if(write(1, buf, n) != n){
    fprintf(2, "write error\en");
    exit();
  }
}

这个代码片段中值得注意的是，cat 并不知道自己是从文件、控制台还是管道读取。同样，cat 也不知道自己是在向控制台、文件还是别的什么打印。文件描述符的使用，以及文件描述符 0 是输入、文件描述符 1 是输出的惯例，使得 cat 的实现非常简单。

close 系统调用释放一个文件描述符，使它可供将来的 open、pipe 或 dup 系统调用（见下文）重新使用。新分配的文件描述符总是当前进程编号最小的未使用描述符。

文件描述符与 fork 的交互使 I/O 重定向易于实现。Fork 连同内存一起复制父进程的文件描述符表，因此子进程一开始就拥有与父进程完全相同的打开文件。系统调用 exec 替换调用进程的内存，但保留它的文件表。这一行为使 shell 能够通过 fork、重新打开选定的文件描述符、然后 exec 新程序来实现 I/O 重定向。下面是 shell 为命令 cat < input.txt 所运行的代码的一个简化版本：

char *argv[2];
argv[0] = "cat";
argv[1] = 0;
if(fork() == 0) {
  close(0);
  open("input.txt", O_RDONLY);
  exec("cat", argv);
}

子进程关闭文件描述符 0 之后，open 保证会为新打开的 input.txt 使用该文件描述符：0 将是最小的可用文件描述符。随后 cat 执行时，文件描述符 0（标准输入）就指向 input.txt。

xv6 shell 中 I/O 重定向的代码正是这样工作的 (8630)。回想一下，在代码中的这一点，shell 已经 fork 出了子 shell，而 runcmd 将调用 exec 加载新程序。现在应该清楚为什么把 fork 和 exec 分成两个调用是个好主意了。因为如果它们是分开的，shell 就可以 fork 一个子进程，在子进程中用 open、close、dup 改变标准输入和输出文件描述符，然后再 exec。被 exec 的程序（在我们的例子中是 cat）不需要做任何改动。如果 fork 和 exec 合并成一个系统调用，那么 shell 就需要某种其他（可能更复杂的）方案来重定向标准输入和输出，或者程序本身必须懂得如何重定向 I/O。

尽管 fork 复制了文件描述符表，但每个底层文件的偏移量在父进程和子进程之间是共享的。考虑下面这个例子：

if(fork() == 0) {
  write(1, "hello ", 6);
  exit();
} else {
  wait();
  write(1, "world\en", 6);
}

在这个片段的末尾，附着在文件描述符 1 上的文件将包含数据 hello world。父进程中的 write（由于 wait，它只在子进程完成后才运行）从子进程的 write 结束的地方继续。这一行为有助于从一系列 shell 命令产生顺序输出，例如 (echo hello; echo world) >output.txt。

dup 系统调用复制一个已有的文件描述符，返回一个指向同一底层 I/O 对象的新描述符。两个文件描述符共享一个偏移量，正如被 fork 复制的文件描述符那样。这是把 hello world 写入文件的另一种方式：

fd = dup(1);
write(1, "hello ", 6);
write(fd, "world\en", 6);

如果两个文件描述符是通过一系列 fork 和 dup 调用从同一个原始文件描述符派生出来的，那么它们共享一个偏移量。否则，即使它们来自对同一文件的 open 调用，文件描述符也不共享偏移量。Dup 使 shell 能够实现这样的命令：ls existing-file non-existing-file > tmp1 2>&1。2>&1 告诉 shell 给该命令一个文件描述符 2，它是描述符 1 的副本。已存在文件的名称和不存在文件的错误消息都会出现在文件 tmp1. 中。xv6 的 shell 不支持对错误文件描述符的 I/O 重定向，但现在你知道如何实现它了。

文件描述符是一种强大的抽象，因为它们隐藏了所连接对象的细节：向文件描述符 1 写入的进程可能是在写文件、写像控制台这样的设备，或者写管道。

管道 ​

管道是一个小的内核缓冲区，以一对文件描述符的形式暴露给进程，一个用于读取，一个用于写入。向管道的一端写入数据，就使该数据可以从管道的另一端读取。管道为进程提供了一种通信方式。

下面的示例代码运行程序 wc，其标准输入连接到管道的读端。

int p[2];
char *argv[2];
argv[0] = "wc";
argv[1] = 0;
pipe(p);
if(fork() == 0) {
  close(0);
  dup(p[0]);
  close(p[0]);
  close(p[1]);
  exec("/bin/wc", argv);
} else {
  close(p[0]);
  write(p[1], "hello world\en", 12);
  close(p[1]);
}

程序调用 pipe，它创建一个新管道，并把读和写的文件描述符记录在数组 p 中。fork 之后，父进程和子进程都有指向该管道的文件描述符。子进程把读端 dup 到文件描述符 0，关闭 p 中的文件描述符，并 exec wc。当 wc 从其标准输入读取时，它就从管道读取。父进程关闭管道的读端，向管道写入，然后关闭写端。

如果没有数据可用，对管道的 read 会等待数据被写入，或者等待所有指向写端的文件描述符被关闭；在后一种情况下，read 将返回 0，就像到达了数据文件的末尾一样。read 会阻塞，直到不可能再有新数据到达，这一事实正是子进程在上面的例子中必须在执行 wc 之前关闭管道写端的原因之一：如果 wc 的某个文件描述符指向管道的写端，wc 就永远看不到文件结束。

xv6 的 shell 以与上面代码类似的方式实现诸如 grep fork sh.c | wc -l 这样的管道 (8650)。子进程创建一个管道，把管道的左端与右端连接起来。然后它为管道的左端调用 fork 和 runcmd，为右端调用 fork 和 runcmd，并等待两者完成。管道的右端可能是一个本身包含管道的命令（例如 a | b | c)），它自己又会 fork 出两个新的子进程（一个用于 b，一个用于 c）。因此，shell 可能创建一棵进程树。这棵树的叶子是命令，内部节点是等待左右子进程完成的进程。原则上，你可以让内部节点运行管道的左端，但正确地这样做会使实现复杂化。

管道似乎并不比临时文件更强大：管道

echo hello world | wc

可以不用管道而实现为

echo hello world >/tmp/xyz; wc </tmp/xyz

在这种情况下，与临时文件相比，管道至少有四个优点。第一，管道会自动清理自己；如果使用文件重定向，shell 就必须小心地在完成后删除 /tmp/xyz。第二，管道可以传递任意长的数据流，而文件重定向需要磁盘上有足够的空闲空间来存储所有数据。第三，管道允许流水线各阶段并行执行，而文件方式要求第一个程序完成后第二个才能开始。第四，如果你在实现进程间通信，管道的阻塞读写比文件的非阻塞语义更高效。

文件系统 ​

xv6 文件系统提供数据文件（即无解释的字节数组）和目录（其中包含对数据文件和其他目录的命名引用）。目录形成一棵树，从称为根的特殊目录开始。像 /a/b/c 这样的路径指的是根目录 / 中名为 a 的目录里名为 b 的目录中名为 c 的文件或目录。不以 / 开头的路径相对于调用进程的当前目录求值，当前目录可以用 chdir 系统调用改变。下面两个代码片段打开同一个文件（假设涉及的所有目录都存在）：

chdir("/a");
chdir("b");
open("c", O_RDONLY);
open("/a/b/c", O_RDONLY);

第一个片段把进程的当前目录改为 /a/b；第二个片段既不引用也不改变进程的当前目录。

有多个系统调用可以创建新文件或目录：mkdir 创建一个新目录，带 O_CREATE 标志的 open 创建一个新数据文件，mknod 创建一个新设备文件。这个例子说明了全部三种：

mkdir("/dir");
fd = open("/dir/file", O_CREATE|O_WRONLY);
close(fd);
mknod("/console", 1, 1);

Mknod 在文件系统中创建一个文件，但该文件没有内容。相反，文件的元数据把它标记为设备文件，并记录主设备号和次设备号（mknod 的两个参数），它们唯一地标识一个内核设备。当进程稍后打开该文件时，内核把 read 和 write 系统调用转交给内核设备实现，而不是传给文件系统。

fstat 检索关于文件描述符所指对象的信息。它填充一个 struct stat，在 stat.h 中定义为：

1234567891011
#define T_DIR  1   // Directory
#define T_FILE 2   // File
#define T_DEV  3   // Device

struct stat {
  short type;  // Type of file
  int dev;     // File system's disk device
  uint ino;    // Inode number
  short nlink; // Number of links to file
  uint size;   // Size of file in bytes
};

文件名与文件本身是不同的事物；同一个底层文件（称为索引节点）可以有多个名字（称为链接）。link 系统调用创建另一个文件系统名字，指向与已有文件相同的索引节点。这个片段创建一个同时名为 a 和 b 的新文件。

open("a", O_CREATE|O_WRONLY);
link("a", "b");

从 a 读取或向 a 写入，与从 b 读取或向 b 写入相同。每个索引节点由一个唯一的索引节点号标识。经过上面的代码序列之后，可以通过检查 fstat 的结果来确定 a 和 b 指向相同的底层内容：两者将返回相同的索引节点号（ino），并且 nlink 计数将被置为 2。

unlink 系统调用从文件系统中删除一个名字。只有当文件的链接数为零且没有文件描述符指向它时，文件的索引节点和保存其内容的磁盘空间才会被释放。因此，在最后一个代码序列中加入

unlink("a");

会使索引节点和文件内容仍可作为 b 访问。此外，

fd = open("/tmp/xyz", O_CREATE|O_RDWR);
unlink("/tmp/xyz");

是一种惯用的方式，用来创建一个临时索引节点，它将在进程关闭 fd 或退出时被清理。

用于文件系统操作的 shell 命令被实现为用户级程序，例如 mkdir、ln、rm 等。这种设计使任何人都能通过添加一个新的用户级程序来用新命令扩展 shell。事后看来这个方案似乎显而易见，但在 Unix 时代设计的其他系统常常把这类命令内置到 shell 中（并把 shell 内置到内核中）。

一个例外是 cd，它内置于 shell 中 (8716)。cd 必须改变 shell 自身的当前工作目录。如果 cd 作为普通命令运行，那么 shell 会 fork 一个子进程，子进程会运行 cd，而 cd 会改变子进程的工作目录。父进程（即 shell）的工作目录不会改变。

现实世界 ​

Unix 把“标准”文件描述符、管道以及便于操作它们的 shell 语法结合在一起，这是编写通用可复用程序方面的一大进步。这一思想激发了一整种“软件工具”文化，Unix 的威力和流行很大程度上归功于这种文化，而 shell 则是第一个所谓的“脚本语言”。Unix 系统调用接口至今仍存在于 BSD、Linux 和 Mac OS X 等系统中。

Unix 系统调用接口已经通过可移植操作系统接口（POSIX）标准加以标准化。xv6 并不符合 POSIX。它缺少一些系统调用（包括 lseek 这样的基本调用），只部分实现了某些系统调用，等等。我们对 xv6 的主要目标是简单和清晰，同时提供一个简单的类 UNIX 系统调用接口。有几个人为 xv6 扩展了少量更基本的系统调用和一个简单的 C 库，以便运行基本的 Unix 程序。然而，与现代内核相比，xv6 提供的系统调用和内核服务种类要少得多。例如，现代内核支持网络、窗口系统、用户级线程、许多设备的驱动，等等。现代内核持续而快速地演进，并提供 POSIX 之外的许多特性。

大体而言，现代派生自 Unix 的操作系统并没有遵循早期 Unix 把设备暴露为特殊文件的模型，比如上面讨论的 console 设备文件。Unix 的作者们后来构建了 Plan 9，它把“资源即文件”的概念应用到现代设施上，把网络、图形和其他资源表示为文件或文件树。

文件系统抽象一直是一个强有力的思想。即便如此，操作系统接口还有其他模型。Multics 是 Unix 的前身，它把文件存储抽象得看起来像内存，产生了风格迥异的接口。Multics 设计的复杂性直接影响了 Unix 的设计者，他们试图构建更简单的东西。

本书考察 xv6 如何实现其类 Unix 接口，但这些思想和概念并不只适用于 Unix。任何操作系统都必须把进程复用到下层硬件上，把进程彼此隔离，并提供受控的进程间通信机制。学习 xv6 之后，你应该能够审视其他更复杂的操作系统，并在那些系统中看到 xv6 背后的概念。
