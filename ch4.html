第 4 章　锁 ​

xv6 运行在多处理器上：这些计算机有多个独立执行的 CPU。这些 CPU 共享物理 RAM，xv6 利用这种共享来维护所有 CPU 都会读写的结构。这种共享带来了这样的可能性：一个 CPU 正在读取某个数据结构，而另一个 CPU 正在更新它，甚至多个 CPU 同时更新同一数据；如果没有谨慎的设计，这种并行访问很可能产生错误的结果或破坏数据结构。即使在单处理器上，如果中断例程与某些可被中断的代码使用相同的数据，而中断恰好在不恰当的时刻发生，也可能破坏数据。

任何并发访问共享数据的代码都必须有在并发情况下保持正确性的策略。并发可能来自多个核的访问、多个线程的访问，或者中断代码。xv6 使用少量简单的并发控制策略；更精细的做法也是可能的。本章聚焦于 xv6 以及许多其他系统中广泛使用的一种策略：锁。

锁提供互斥，确保同一时刻只有一个 CPU 能持有该锁。如果每个共享数据项都关联一把锁，并且代码在使用某个数据项时总是持有相应的锁，那么我们就可以确信该数据项在同一时刻只被一个 CPU 使用。在这种情况下，我们说这把锁保护该数据项。

本章余下部分解释 xv6 为什么需要锁、xv6 如何实现锁，以及如何使用锁。一个关键的观察是：当你查看 xv6 中的某段代码时，必须问自己，另一个处理器（或中断）是否可能通过修改该代码所依赖的数据（或硬件资源）而改变代码的预期行为。你必须记住，一条 C 语句可能对应若干条机器指令，因此另一个处理器或中断可能在一条 C 语句执行到一半时插进来。你不能假定纸面上的代码行是原子执行的。并发使关于正确性的推理困难得多。

竞态条件 ​

作为为什么需要锁的一个例子，考虑多个处理器共享一块磁盘，例如 xv6 中的 IDE 磁盘。磁盘驱动维护一个未完成磁盘请求的链表 (4226)，处理器可能并发地向该链表添加新请求 (4354)。如果没有并发请求，你可能会这样实现该链表：

1234567891011121314151617
struct list {
  int data;
  struct list *next;
};

struct list *list = 0;

void
insert(int data)
{
  struct list *l;

  l = malloc(sizeof *l);
  l->data = data;
  l->next = list;
  list = l;
}

如果在隔离状态下执行，这个实现是正确的。然而，如果有多份副本并发执行，这段代码就不正确了。如果两个 CPU 同时执行 insert，可能出现两者都在执行第 16 行之前执行了第 15 行的情况（见 图 4-1）。如果发生这种情况，现在就会有两个链表节点的 next 被设为 list 的原值。当第 16 行的两次赋值发生时，第二次会覆盖第一次；第一次赋值涉及的节点就会丢失。

第 16 行的丢失更新是竞态条件的一个例子。竞态条件是指一个内存位置被并发访问，且至少有一次访问是写。竞态往往是缺陷的征兆，要么是丢失更新（如果访问是写），要么是读到一个未完全更新的数据结构。竞态的结果取决于两个相关 CPU 的精确时序以及内存系统如何排序它们的内存操作，这可能使竞态引起的错误难以重现和调试。例如，在调试 insert 时加入打印语句，可能足以改变执行的时序，使竞态消失。

避免竞态的常用方法是使用锁。锁确保互斥，使同一时刻只有一个 CPU 能执行 insert；这使上述情形不可能发生。上面代码正确加锁的版本只需增加几行（未编号）：

67891011121314151617
struct list *list = 0;
     	struct lock listlock;

void
insert(int data)
{
  struct list *l;
  l = malloc(sizeof *l);
  l->data = data;

     	  acquire(&listlock);
  l->next = list;
  list = l;
     	  release(&listlock);
}

acquire 与 release 之间的指令序列通常称为临界区，而锁保护的是 list。

当我们说一把锁保护数据时，真正的意思是这把锁保护适用于该数据的一组不变量。不变量是数据结构在操作之间保持的性质。通常，一个操作的正确行为取决于操作开始时这些不变量为真。操作可能暂时违反不变量，但必须在结束前重新建立它们。例如，在链表的情形中，不变量是 list 指向链表的第一个节点，且每个节点的 next 字段指向下一个节点。insert 的实现暂时违反了这个不变量：在第 15 行，l 指向下一个链表元素，但 list 尚未指向 l（在第 16 行重新建立）。我们上面考察的竞态之所以发生，是因为第二个 CPU 在不变量（暂时）被违反期间执行了依赖链表不变量的代码。正确使用锁可以确保同一时刻只有一个 CPU 能在临界区中操作该数据结构，从而不会有 CPU 在数据结构的不变量不成立时执行数据结构操作。

你可以把锁看作把并发的临界区串行化，使它们一次运行一个，从而保持不变量（假定它们在隔离状态下是正确的）。你也可以把各个临界区看作彼此原子，这样后获得锁的临界区只会看到较早临界区完成的全部修改，而绝不会看到部分完成的更新。

注意，把 acquire 移到 insert 中更早的位置也是正确的。例如，把对 acquire 的调用移到第 12 行之前是没问题的。这可能会降低并行度，因为那样对 malloc 的调用也被串行化了。下面的“使用锁”一节给出了一些关于在何处插入 acquire 和 release 调用的指导。

代码：锁 ​

xv6 有两类锁：自旋锁和睡眠锁。我们从自旋锁开始。xv6 用 struct spinlock (1501) 表示自旋锁。结构中重要的字段是 locked，当锁可用时这个字为零，被持有时非零。从逻辑上说，xv6 应当通过执行类似下面的代码来获取锁：

21222324252627282930
void
acquire(struct spinlock *lk)
{
  for(;;) {
    if(!lk->locked) {
      lk->locked = 1;
      break;
    }
  }
}

不幸的是，这个实现在多处理器上不能保证互斥。可能出现两个 CPU 同时到达第 25 行，看到 lk->locked 为零，然后都通过执行第 26 行抢到锁。此时，两个不同的 CPU 都持有该锁，违反了互斥性质。这个 acquire 实现非但没有帮助我们避免竞态条件，反而有它自己的竞态条件。问题在于第 25 行和第 26 行是作为两个独立动作执行的。要使上面的例程正确，第 25 行和第 26 行必须在一个原子（即不可分割）步骤中执行。

为了原子地执行这两行，xv6 依赖一条特殊的 x86 指令 xchg (0569)。在一次原子操作中，xchg 把内存中的一个字与一个寄存器的内容交换。函数 acquire (1580) 在循环中重复这条 xchg 指令；每次迭代都原子地读取 lk->locked 并把它设为 1 (1587)。如果锁已被持有，lk->locked 已经是 1，因此 xchg 返回 1，循环继续。然而，如果 xchg 返回 0，acquire 就成功获得了锁——locked 原来是 0，现在是 1——因此循环可以停止。获得锁之后，acquire 出于调试目的记录获得该锁的 CPU 和栈回溯。如果某个进程忘记释放锁，这些信息有助于找出罪魁祸首。这些调试字段受该锁保护，只能在持有锁时修改。

函数 release (1602) 与 acquire 相反：它清除调试字段，然后释放锁。该函数使用一条汇编指令来清除 locked，因为清除该字段应当是原子的，这样 xchg 指令就不会看到存放 locked 的 4 个字节中只有一部分被更新。x86 保证 32 位的 movl 原子地更新全部 4 个字节。xv6 不能使用普通的 C 赋值，因为 C 语言规范并未规定单次赋值是原子的。

xv6 的自旋锁实现是 x86 特有的，因此 xv6 不能直接移植到其他处理器。为了允许可移植的自旋锁实现，C 语言支持一个原子指令库；可移植的操作系统会使用那些指令。

代码：使用锁 ​

xv6 在许多地方使用锁来避免竞态条件。一个简单的例子在 IDE 驱动中。正如本章开头提到的，iderw (4354) 有一个磁盘请求队列，处理器可能并发地向该链表添加新请求 (4369)。为了保护这个链表以及驱动中的其他不变量，iderw 获取 idelock (4365)，并在函数结束时释放它。

练习 1 探讨如何通过把 acquire 移到队列操作之后来触发我们在本章开头看到的 IDE 驱动竞态条件。这个练习值得一试，因为它会清楚地表明，触发该竞态并不那么容易，这说明发现竞态条件缺陷很困难。xv6 中存在一些竞态并非不可能。

使用锁的一个难点是决定用多少把锁，以及每把锁保护哪些数据和不变量。有几条基本原则。第一，只要一个变量可能在一个 CPU 写入的同时被另一个 CPU 读取或写入，就应当引入一把锁来防止这两个操作重叠。第二，记住锁保护的是不变量：如果一个不变量涉及多个内存位置，通常需要用同一把锁保护所有这些位置，以确保该不变量得以维持。

上述规则说明了何时需要锁，但没有说明何时不需要锁；为了效率，重要的是不要锁得太多，因为锁会降低并行度。如果并行度不重要，那么可以安排只有一个线程，从而不必担心锁。一个简单的内核可以在多处理器上做到这一点：只用一把锁，进入内核时必须获取，退出内核时释放（不过像管道读取或 wait 这样的系统调用会带来问题）。许多单处理器操作系统就是用这种方法改造成在多处理器上运行的，这种方法有时称为“大内核锁”，但它牺牲了并行度：同一时刻只有一个 CPU 能在内核中执行。如果内核要做大量计算，使用一组数量更多、粒度更细的锁会更高效，这样内核就能在多个 CPU 上同时执行。

归根结底，锁粒度的选择是一项并行编程的练习。xv6 使用少量粗粒度的、针对特定数据结构的锁（见 图 4-2）。例如，xv6 有一把锁保护整个进程表及其不变量，这些不变量在 第 5 章 中描述。更细粒度的做法是为进程表中的每个表项各配一把锁，这样处理不同表项的线程就能并行推进。然而，这会使那些具有跨整个进程表不变量的操作复杂化，因为它们可能不得不获取多把锁。后续各章将讨论 xv6 的每一部分如何处理并发，展示如何使用锁。

死锁与锁顺序 ​

如果一条穿过内核的代码路径必须同时持有多把锁，那么所有代码路径都以相同顺序获取这些锁就很重要。如果它们不这样做，就有死锁的风险。假设 xv6 中有两条代码路径需要锁 A 和 B，但代码路径 1 按 A 然后 B 的顺序获取，另一条路径按 B 然后 A 的顺序获取。如果两个线程并发执行这两条代码路径，这种情况可能导致死锁。假设线程 T1 执行代码路径 1 并获取锁 A，线程 T2 执行代码路径 2 并获取锁 B。接着 T1 将尝试获取锁 B，T2 将尝试获取锁 A。两次获取都会无限期阻塞，因为在两种情况下另一个线程都持有所需的锁，并且在它的 acquire 返回之前不会释放。为了避免这种死锁，所有代码路径都必须以相同顺序获取锁。需要全局的锁获取顺序，这意味着锁实际上是每个函数规范的一部分：调用者必须以这样的方式调用函数，使得锁按约定的顺序被获取。

由于 第 5 章 所讨论的 sleep 的工作方式，xv6 有许多涉及 ptable.lock、长度为 2 的锁顺序链。例如，ideintr 在调用 wakeup 时持有 ide 锁，而 wakeup 会获取 ptable 锁。文件系统代码包含 xv6 中最长的锁链。例如，创建一个文件需要同时持有目录上的锁、新文件索引节点上的锁、某个磁盘块缓冲区上的锁、idelock 以及 ptable.lock。为了避免死锁，文件系统代码总是按上一句提到的顺序获取锁。

中断处理程序 ​

xv6 在许多情况下使用自旋锁来保护中断处理程序和线程都会使用的数据。例如，定时器中断可能在 (3414) 递增 ticks，而几乎同时某个内核线程在 sys_sleep (3823) 中读取 ticks。锁 tickslock 把这两次访问串行化。

中断即使在单处理器上也能引起并发：如果中断被启用，内核代码可能在任意时刻被停下，转而运行中断处理程序。假设 iderw 持有 idelock，然后被中断去运行 ideintr。Ideintr 会试图锁住 idelock，发现它已被持有，然后等待它被释放。在这种情况下，idelock 将永远不会被释放——只有 iderw 能释放它，而 iderw 在 ideintr 返回之前不会继续运行——因此处理器乃至整个系统将死锁。

为了避免这种情况，如果某个自旋锁会被中断处理程序使用，处理器就绝不能在启用中断的情况下持有该锁。xv6 更加保守：当处理器进入自旋锁临界区时，xv6 总是确保该处理器上的中断被禁用。其他处理器上仍可能发生中断，因此中断处理程序中的 acquire 可以等待某个线程释放自旋锁；只是不能在同一处理器上等待。

当处理器不持有任何自旋锁时，xv6 会重新启用中断；它必须做一些记录工作来应对嵌套的临界区。acquire 调用 pushcli (1667)，release 调用 popcli (1679)，以跟踪当前处理器上锁的嵌套层数。当该计数达到零时，popcli 恢复最外层临界区开始时的中断启用状态。cli 和 sti 函数分别执行 x86 的禁用中断和启用中断指令。

重要的是，acquire 必须在可能获得锁的 xchg 之前调用 pushcli (1587)。如果两者顺序颠倒，就会有若干个指令周期是在中断启用的情况下持有锁，一次时机不幸的中断将使系统死锁。同样重要的是，release 只能在释放锁的 xchg 之后调用 popcli (1587)。

指令与内存顺序 ​

本章一直假定代码按照程序中的顺序执行。然而，许多编译器和处理器会乱序执行代码以获得更高的性能。如果一条指令需要很多周期才能完成，处理器可能希望提早发出该指令，以便与其他指令重叠、避免处理器停顿。例如，处理器可能注意到在一串连续的指令中 A 和 B 互不依赖，于是在 A 之前开始执行 B，以便在处理器完成 A 时 B 也已完成。编译器也可能通过在可执行文件中先发出指令 B 再发出指令 A 来执行类似的重新排序。然而，并发可能把这种重排序暴露给软件，从而导致错误的行为。

例如，在下面这段 insert 的代码中，如果编译器或处理器使第 4 行（或第 2 行、第 5 行）的效果在第 6 行的效果之后才对其他核可见，那将是一场灾难：

123456
  l = malloc(sizeof *l);
  l->data = data;
  acquire(&listlock);
  l->next = list;
  list = l;
  release(&listlock);

如果硬件或编译器重新排序，例如使第 4 行的效果在第 6 行之后才可见，那么另一个处理器可以获得 listlock，观察到 list 指向 l，却观察不到 l->next 已被设为链表的其余部分，因而无法读取链表的其余部分。

为了告诉硬件和编译器不要执行这样的重排序，xv6 在 acquire 和 release 中都使用 __sync_synchronize()。_sync_synchronize() 是一个内存屏障：它告诉编译器和 CPU 不要跨越屏障重排加载或存储。xv6 只在 acquire 和 release 中关心顺序，因为对锁结构之外的数据结构的并发访问都是在 acquire 和 release 之间进行的。

睡眠锁 ​

有时 xv6 代码需要长时间持有一把锁。例如，文件系统（第 6 章）在磁盘上读写文件内容期间保持该文件加锁，而这些磁盘操作可能需要几十毫秒。效率要求等待时让出处理器，以便其他线程取得进展，这又意味着 xv6 需要能在跨越上下文切换持有时正常工作的锁。xv6 以睡眠锁的形式提供这样的锁。

xv6 睡眠锁支持在其临界区内让出处理器。这一性质带来了一个设计挑战：如果线程 T1 持有锁 L1 并已让出处理器，而线程 T2 希望获取 L1，我们必须确保 T1 能在 T2 等待期间执行，以便 T1 能释放 L1。T2 在这里不能使用自旋锁的获取函数：它在关闭中断的情况下自旋，而那会阻止 T1 运行。为了避免这种死锁，睡眠锁的获取例程（称为 acquiresleep）在等待时让出处理器，并且不关闭中断。

acquiresleep (4622) 使用了将在 第 5 章 中解释的技术。概括地说，睡眠锁有一个由自旋锁保护的 locked 字段，acquiresleep 对 sleep 的调用会原子地让出 CPU 并释放自旋锁。结果是，其他线程可以在 acquiresleep 等待期间执行。

由于睡眠锁让中断保持启用，它们不能用于中断处理程序。由于 acquiresleep 可能让出处理器，睡眠锁不能在自旋锁临界区内使用（不过自旋锁可以在睡眠锁临界区内使用）。

xv6 在大多数情况下使用自旋锁，因为它们的开销较低。它只在文件系统中使用睡眠锁，因为在那里能够跨越漫长的磁盘操作持有锁很方便。

锁的局限 ​

锁往往能干净地解决并发问题，但有时它们也很别扭。后续各章会指出 xv6 中的这类情形；本节概述会出现的一些问题。

有时一个函数使用的数据必须由锁保护，但该函数既会被已经持有该锁的代码调用，也会被本来不需要该锁的代码调用。应对这一点的一种办法是为该函数提供两个变体，一个负责获取锁，另一个则期望调用者已经持有锁；wakeup1 就是一个例子 (2953)。另一种办法是要求调用者无论是否需要都持有该锁，sched (2758) 就是如此。内核开发者需要了解这类要求。

看起来可以通过允许递归锁来简化调用者和被调用者都需要锁的情形：如果一个函数持有锁，它调用的任何函数都被允许再次获取该锁。然而，程序员那时就需要对所有调用者与被调用者的组合进行推理，因为在 acquire 之后数据结构的不变量将不再总是成立。递归锁是否优于 xv6 所采用的、关于“要求持有锁的函数”的约定，并不清楚。更大的教训是（如同为避免死锁而采用的全局锁顺序一样），锁的要求有时无法保持私有，而会侵入函数和模块的接口。

锁不足的一种情形是：一个线程需要等待另一个线程对数据结构的更新，例如管道的读者等待某个其他线程向管道写入。等待的线程不能持有该数据的锁，因为那会阻止它所等待的更新。作为替代，xv6 提供了一种单独的机制来联合管理锁和事件等待；见 第 5 章 中对 sleep 和 wakeup 的描述。

现实世界 ​

并发原语和并行编程是活跃的研究领域，因为用锁编程仍然具有挑战性。最好把锁用作同步队列等更高层构造的基础，尽管 xv6 并没有这样做。如果你用锁编程，明智的做法是使用试图找出竞态条件的工具，因为很容易漏掉某个需要锁的不变量。

大多数操作系统支持 POSIX 线程（Pthreads），它允许一个用户进程在多个处理器上并发运行多个线程。Pthreads 支持用户级锁、屏障等。支持 Pthreads 需要操作系统的支持。例如，应当做到：如果一个 pthread 在系统调用中阻塞，同一进程的另一个 pthread 应当能够在该处理器上运行。再比如，如果一个 pthread 改变了其进程的地址空间（例如扩大或缩小它），内核必须安排运行同一进程线程的其他处理器更新它们的硬件页表，以反映地址空间的变化。在 x86 上，这涉及使用处理器间中断（IPI）击落其他处理器的转译后备缓冲区（TLB）。

不使用原子指令也可以实现锁，但代价高昂，大多数操作系统都使用原子指令。

如果许多处理器同时试图获取同一把锁，锁的代价可能很高。如果一个处理器把某把锁缓存在它的本地缓存中，而另一个处理器必须获取该锁，那么用于更新存放该锁的缓存行的原子指令必须把该行从一个处理器的缓存移到另一个处理器的缓存，并且可能使该缓存行的其他副本失效。从另一个处理器的缓存中取一个缓存行，可能比从本地缓存中取一行昂贵几个数量级。

为了避免与锁相关的开销，许多操作系统使用无锁的数据结构和算法。例如，可以实现本章开头那样的链表，使得在链表中搜索时无需加锁，而插入一项只需一条原子指令。然而，无锁编程比用锁编程更复杂；例如，必须担心指令和内存的重排序。用锁编程已经很难，因此 xv6 避免了无锁编程的额外复杂性。

练习 ​

  1. 把 iderw 中的 acquire 移到 sleep 之前。存在竞态吗？为什么在启动 xv6 并运行 stressfs 时观察不到它？用一个哑循环扩大临界区；现在你看到了什么？请解释。

  2. 删除 acquire 中的 xchg。解释运行 xv6 时会发生什么？

  3. 使用 POSIX 线程编写一个并行程序，大多数操作系统都支持它。例如，实现一个并行哈希表，并测量 put/get 的吞吐量是否随核数增加而扩展。

  4. 在 xv6 中实现 Pthreads 的一个子集。也就是说，实现一个用户级线程库，使用户进程可以拥有多于 1 个线程，并安排这些线程能在不同处理器上并行运行。设计一个方案，正确处理线程发起阻塞系统调用以及改变其共享地址空间的情况。
