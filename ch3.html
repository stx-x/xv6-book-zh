第 3 章　陷阱、中断与驱动 ​

CPU 运行进程时执行的是正常的处理器循环：读一条指令、推进程序计数器、执行该指令，然后重复。但有些事件会使控制权必须从用户程序转回内核，而不是继续执行下一条指令。这些事件包括：设备发出信号表示需要关注、用户程序做了非法的事情（例如引用一个没有页表项的虚拟地址），或者用户程序通过系统调用请求内核提供服务。处理这些事件有三项主要挑战：1）内核必须安排处理器从用户模式切换到内核模式（以及切回）；2）内核与设备必须协调它们并行的活动；3）内核必须理解设备的接口。应对这三项挑战需要详细理解硬件并谨慎编程，而且可能导致内核代码晦涩难懂。本章解释 xv6 如何应对这三项挑战。

系统调用、异常与中断 ​

有三种情况需要把控制权从用户程序转移到内核。第一，系统调用：用户程序请求操作系统服务，正如我们在上一章末尾看到的。第二，异常：程序执行了非法动作。非法动作的例子包括除以零、试图访问一个页表项不存在的内存，等等。第三，中断：设备产生一个信号，表示它需要操作系统的关注。例如，时钟芯片可能每 100 毫秒产生一次中断，以便内核实现分时。再比如，磁盘从磁盘读出一个块后，会产生一次中断，通知操作系统该块已可读取。

内核处理所有中断，而不是由进程来处理，因为在大多数情况下只有内核拥有所需的特权和状态。例如，为了响应时钟中断而在进程之间分时，内核必须参与，哪怕只是为了强制不合作的进程让出处理器。

在这三种情况下，操作系统的设计都必须安排以下事情发生。系统必须保存处理器的寄存器，以便将来透明地恢复。系统必须为在内核中执行做好准备。系统必须为内核选择一个开始执行的位置。内核必须能够获取关于该事件的信息，例如系统调用的参数。这一切都必须安全地完成；系统必须保持用户进程与内核的隔离。

为了实现这个目标，操作系统必须了解硬件处理系统调用、异常和中断的细节。在大多数处理器中，这三类事件由同一套硬件机制处理。例如，在 x86 上，程序通过 int 指令产生一个中断来发起系统调用。类似地，异常也会产生中断。因此，如果操作系统有一套处理中断的方案，它也就能够处理系统调用和异常。

基本方案如下。中断停止正常的处理器循环，并开始执行一段新的序列，称为中断处理程序。在开始执行中断处理程序之前，处理器保存自己的寄存器，以便操作系统在从中断返回时恢复它们。进出中断处理程序的转换有一个难点：处理器应当从用户模式切换到内核模式，然后再切回。

关于术语的一点说明：尽管 x86 的正式术语是异常（exception），xv6 使用的术语是陷阱（trap），这主要是因为 PDP11/40 使用了这个术语，因而它成为 Unix 的惯用术语。此外，本章会交替使用陷阱和中断这两个词，但要记住一个重要区别：陷阱由当前正在处理器上运行的进程引起（例如进程发起系统调用，从而产生一个陷阱），而中断由设备引起，可能与当前正在运行的进程无关。例如，磁盘在为一个进程读取完一个块时可能产生中断，但在中断发生时，正在运行的可能是另一个进程。中断的这一性质使得思考中断比思考陷阱更困难，因为中断与其他活动并发发生。不过，两者都依赖同一套硬件机制在用户模式和内核模式之间安全地转移控制权，我们接下来讨论这一点。

x86 保护 ​

x86 有 4 个保护级，编号 0（特权最高）到 3（特权最低）。在实践中，大多数操作系统只使用 2 个级别：0 和 3，它们分别称为内核模式和用户模式。x86 执行指令时所用的当前特权级存储在 cs 寄存器的 CPL 字段中。

在 x86 上，中断处理程序定义在中断描述符表（IDT）中。IDT 有 256 个表项，每个表项给出处理相应中断时要使用的 cs 和 eip。

要在 x86 上发起系统调用，程序调用 int n 指令，其中 n 指定 IDT 中的索引。int 指令执行以下步骤：

  • 从 IDT 中取出第 n 个描述符，其中 n 是 int 的参数。
  • 检查 cs 中的 CPL <= DPL，其中 DPL 是描述符中的特权级。
  • 把 esp 和 ss 保存到 CPU 内部寄存器中，但仅当目标段选择子的 PL < CPL 时才这样做。
  • 从任务段描述符中加载 ss 和 esp。
  • 压入 ss。
  • 压入 esp。
  • 压入 eflags。
  • 压入 cs。
  • 压入 eip。
  • 清除 eflags 中的 IF 位，但仅在中断时这样做。
  • 把 cs 和 eip 设为描述符中的值。

int 指令是一条复杂的指令，人们可能会问这些动作是否都必要。例如，检查 CPL <= DPL 使内核能够禁止对不恰当的 IDT 表项（例如设备中断处理程序）发起 int 调用。用户程序要执行 int，IDT 表项的 DPL 必须是 3。如果用户程序没有相应的特权，int 将导致 int 13，即通用保护错误。再比如，int 指令不能使用用户栈来保存值，因为进程可能没有有效的栈指针；硬件改用任务段中指定的栈，而该栈由内核设置。

图 3-1 展示了 int 指令完成且发生了特权级变化（描述符中的特权级低于 CPL）之后的栈。如果 int 指令不需要特权级变化，x86 就不会保存 ss 和 esp。在两种情况下，eip 都指向描述符表中指定的地址，该地址处的指令就是下一条要执行的指令，也是 int n 处理程序的第一条指令。实现这些处理程序是操作系统的职责，下面我们将看到 xv6 是怎么做的。

操作系统可以使用 iret 指令从 int 指令返回。它从栈上弹出 int 指令期间保存的值，并在保存的 eip 处恢复执行。

代码：第一次系统调用 ​

第 1 章 以 initcode.S 发起系统调用结束。我们再来看一次。进程把 exec 调用的参数压入进程的栈，并把系统调用号放入 eax。系统调用号与 syscalls 数组（一张函数指针表）中的表项对应。我们需要安排 int 指令把处理器从用户模式切换到内核模式，安排内核调用正确的内核函数（即 sys_exec），并安排内核能够取到 sys_exec 的参数。接下来几小节描述 xv6 如何为系统调用做这些安排，然后我们会发现，同样的代码可以复用于中断和异常。

代码：汇编陷阱处理程序 ​

xv6 必须设置 x86 硬件，使其在遇到 int 指令（它使处理器产生一个陷阱）时做出合理的反应。x86 允许 256 种不同的中断。中断 0–31 定义为软件异常，例如除零错误或试图访问无效内存地址。xv6 把 32 个硬件中断映射到 32–63 范围，并使用中断 64 作为系统调用中断。

Tvinit (3382) 由 main 调用，设置 idt 表中的 256 个表项。中断 i 由 vectors[i] 中地址处的代码处理。每个入口点都不同，因为 x86 不会把陷阱号传给中断处理程序。使用 256 个不同的处理程序是区分这 256 种情况的唯一办法。

Tvinit 对 T_SYSCALL（用户系统调用陷阱）做特殊处理：它把值 1 作为第二个参数传入，指定该门为“陷阱”类型。陷阱门不清除 IF 标志，允许在系统调用处理程序执行期间发生其他中断。

内核还把系统调用门的特权设为 DPL_USER，这允许用户程序用显式的 int 指令产生该陷阱。xv6 不允许进程用 int 引发其他中断（例如设备中断）；如果它们尝试，就会遇到通用保护异常，该异常转到向量 13。

当把保护级从用户模式切换到内核模式时，内核不应使用用户进程的栈，因为它可能无效。用户进程可能是恶意的，或者含有错误，导致用户 esp 含有一个不属于该进程用户内存的地址。xv6 通过建立一个任务段描述符来编程 x86 硬件，使其在陷阱时进行栈切换；硬件通过该描述符加载栈段选择子和新的 esp 值。函数 switchuvm (1860) 把用户进程内核栈顶的地址存入任务段描述符。

发生陷阱时，处理器硬件执行以下动作。如果处理器在用户模式下执行，它从任务段描述符加载 esp 和 ss，把旧的用户 ss 和 esp 压入新栈。如果处理器在内核模式下执行，上述动作都不会发生。然后处理器压入 eflags、cs 和 eip 寄存器。对于某些陷阱（例如页错误），处理器还会压入一个错误字。接着处理器从相关的 IDT 表项加载 eip 和 cs。

xv6 使用一个 Perl 脚本生成 IDT 表项所指向的入口点。每个入口点在处理器没有压入错误码时压入一个错误码，压入中断号，然后跳转到 alltraps。

Alltraps (3304) 继续保存处理器寄存器：它压入 ds、es、fs、gs 以及通用寄存器 (3305-3310)。这样做的结果是，内核栈现在包含一个 struct trapframe (0602)，其中保存着陷阱发生时的处理器寄存器（见 图 3-2）。处理器压入 ss、esp、eflags、cs 和 eip。处理器或陷阱向量压入错误号，alltraps 压入其余部分。陷阱帧包含在内核返回当前进程时恢复用户模式处理器寄存器所需的全部信息，使处理器能够完全按照陷阱开始时的状态继续执行。回想 第 2 章，userinit 手工构造了一个陷阱帧来达到这个目的（见 图 1-4）。

对于第一次系统调用，保存的 eip 是 int 指令之后那条指令的地址。cs 是用户代码段选择子。eflags 是执行 int 指令那一刻 eflags 寄存器的内容。在保存通用寄存器的过程中，alltraps 也保存了 eax，其中含有供内核稍后检查的系统调用号。

既然用户模式的处理器寄存器已经保存，alltraps 就可以完成设置，让处理器运行内核 C 代码。处理器在进入处理程序之前已经设置了选择子 cs 和 ss；alltraps 设置 ds 和 es。

段设置妥当之后，alltraps 就可以调用 C 陷阱处理程序 trap。它把 esp（指向它刚刚构造的陷阱帧）作为参数压入栈，然后调用 trap (3319)。trap 返回后，alltraps 通过增加栈指针把参数弹出栈 (3320)，然后开始执行标号 trapret 处的代码。我们在 第 2 章 中追踪过这段代码，当时第一个用户进程运行它以退出到用户空间。同样的序列在这里发生：通过陷阱帧逐项弹出，恢复用户模式寄存器，然后 iret 跳回用户空间。

到目前为止的讨论都针对用户模式下发生的陷阱，但陷阱也可能在内核执行时发生。在这种情况下，硬件不切换栈，也不保存栈指针或栈段选择子；除此之外，其余步骤与用户模式下的陷阱相同，执行的也是同一套 xv6 陷阱处理代码。当 iret 稍后恢复内核模式的 cs 时，处理器继续在内核模式下执行。

代码：C 陷阱处理程序 ​

我们在上一节看到，每个处理程序都会建立一个陷阱帧，然后调用 C 函数 trap。Trap 查看硬件陷阱号 tf->trapno，以判断自己为什么被调用以及需要做什么。如果陷阱是 T_SYSCALL，trap 就调用系统调用处理程序 syscall。我们将在 第 5 章 重新讨论 proc->killed 检查。

在检查完系统调用之后，trap 查找硬件中断（我们在下面讨论）。除了预期的硬件设备之外，陷阱还可能由伪中断引起，即不需要的硬件中断。

如果陷阱既不是系统调用，也不是寻求关注的硬件设备，trap 就假定它是由陷阱之前正在执行的代码的不当行为（例如除以零）引起的。如果引起陷阱的代码是用户程序，xv6 打印详细信息，然后设置 proc->killed，以记住要清理该用户进程。我们将在 第 5 章 中考察 xv6 如何完成这项清理。

如果是内核在运行，那必定是内核的缺陷：trap 打印关于这一意外情况的详细信息，然后调用 panic。

代码：系统调用 ​

对于系统调用，trap 调用 syscall。Syscall 从陷阱帧（其中含有保存的 eax）加载系统调用号，并索引系统调用表。对于第一次系统调用，eax 含有值 SYS_exec，syscall 将调用系统调用表的第 SYS_exec 项，这对应于调用 sys_exec。

Syscall 把系统调用函数的返回值记录在 eax 中。当陷阱返回用户空间时，它会从 cp->tf 把值装入机器寄存器。因此，当 exec 返回时，它将返回系统调用处理程序所返回的值。按照惯例，系统调用返回负数表示错误，返回正数表示成功。如果系统调用号无效，syscall 打印一条错误并返回 -1。

后续各章将考察特定系统调用的实现。本章关注的是系统调用的机制。还剩下一点机制：找到系统调用的参数。辅助函数 argint、argptr、argstr 和 argfd 取出第 n 个系统调用参数，分别作为整数、指针、字符串或文件描述符。argint 使用用户空间的 esp 寄存器来定位第 n 个参数：esp 指向系统调用存根的返回地址。参数就在它上面，位于 esp+4。于是第 n 个参数位于 esp+4+4*n。

argint 调用 fetchint 从用户内存读取该地址处的值并写入 *ip。fetchint 可以直接把地址转换为指针，因为用户和内核共享同一张页表，但内核必须验证该指针位于地址空间的用户部分之内。内核已经设置好页表硬件，确保进程无法访问其本地私有内存之外的内存：如果用户程序试图读写 p->sz 或更高地址处的内存，处理器将产生一个段陷阱，而 trap 会杀死该进程，正如我们在上面看到的。然而，内核可以解引用用户可能传入的任何地址，因此它必须显式检查该地址低于 p->sz。

argptr 取出第 n 个系统调用参数，并检查该参数是一个有效的用户空间指针。注意，调用 argptr 期间会发生两次检查。首先，在取出参数的过程中检查用户栈指针。然后检查该参数本身，它也是一个用户指针。

argstr 把第 n 个参数解释为指针。它确保该指针指向一个以 NUL 结尾的字符串，并且整个字符串位于地址空间用户部分的末尾之下。

最后，argfd (6084) 使用 argint 取出一个文件描述符编号，检查它是否是有效的文件描述符，并返回相应的 struct file。

系统调用的实现（例如 sysproc.c 和 sysfile.c）通常是包装函数：它们用 argint、argptr 和 argstr 解码参数，然后调用真正的实现。在 第 2 章 中，sys_exec 使用这些函数来取得它的参数。

代码：中断 ​

主板上的设备可以产生中断，xv6 必须设置硬件来处理这些中断。设备通常产生中断是为了告诉内核某个硬件事件已经发生，例如 I/O 完成。中断通常是可选的，意思是内核也可以改为定期检查（或“轮询”）设备硬件以查看新事件。如果事件相对稀少，中断比轮询更可取，因为轮询会浪费 CPU 时间。中断处理复用了系统调用和异常已经需要的部分代码。

中断与系统调用类似，区别在于设备会在任意时刻产生中断。主板上有一块硬件，在设备需要关注时（例如用户在键盘上敲了一个字符）向 CPU 发出信号。我们必须编程设备使其产生中断，并安排某个 CPU 接收该中断。

我们来看定时器设备和定时器中断。我们希望定时器硬件每秒产生大约 100 次中断，以便内核跟踪时间的流逝，并能在多个正在运行的进程之间分时。选择每秒 100 次可以在获得不错的交互性能的同时，不至于让处理器忙于处理中断。

与 x86 处理器本身一样，PC 主板也在演进，提供中断的方式也随之演进。早期主板有一个简单的可编程中断控制器（称为 PIC）。随着多处理器 PC 主板的出现，需要一种新的中断处理方式，因为每个 CPU 都需要一个中断控制器来处理发送给它的中断，而且必须有把中断路由到处理器的办法。这种方式由两部分组成：一部分位于 I/O 系统中（IO APIC，ioapic.c），另一部分附属于每个处理器（本地 APIC，lapic.c）。xv6 是为多处理器主板设计的：它忽略来自 PIC 的中断，并配置 IOAPIC 和本地 APIC。

IO APIC 有一张表，处理器可以通过内存映射 I/O 编程表中的表项。初始化期间，xv6 编程把中断 0 映射到 IRQ 0，依此类推，但把它们全部禁用。特定设备会启用特定的中断，并指明该中断应当路由到哪个处理器。例如，xv6 把键盘中断路由到处理器 0 (8274)。xv6 把磁盘中断路由到系统中编号最高的处理器，我们将在下面看到。

定时器芯片位于 LAPIC 内部，因此每个处理器都可以独立地接收定时器中断。xv6 在 lapicinit (7408) 中设置它。关键的一行是编程定时器的那一行 (7421)。这一行告诉 LAPIC 在 IRQ_TIMER（即 IRQ 0）上定期产生中断。第 (7451) 行启用某个 CPU 的 LAPIC 上的中断，这将使它把中断递送给本地处理器。

处理器可以通过 eflags 寄存器中的 IF 标志控制自己是否愿意接收中断。指令 cli 通过清除 IF 禁用处理器上的中断，sti 则启用处理器上的中断。xv6 在主 CPU 启动时 (9112) 和其他处理器启动时 (1124) 禁用中断。每个处理器上的调度器会启用中断 (2766)。为了控制某些代码片段不被中断，xv6 在这些代码片段期间禁用中断（例如见 switchuvm (1860)）。

定时器通过向量 32（xv6 选择用它处理 IRQ 0）产生中断，xv6 在 idtinit (1255) 中设置它。向量 32 与向量 64（用于系统调用的那个）唯一的区别是，向量 32 是中断门而不是陷阱门。中断门会清除 IF，使被中断的处理器在处理当前中断期间不会接收中断。从这里开始直到 trap，中断走的代码路径与系统调用和异常相同，都会建立陷阱帧。

对于定时器中断，Trap 只做两件事：递增 ticks 变量 (3417)，并调用 wakeup。正如我们将在 第 5 章 中看到的，后者可能导致中断返回时切换到另一个进程。

驱动 ​

驱动是操作系统中管理特定设备的代码：它告诉设备硬件执行操作，配置设备在完成时产生中断，并处理由此产生的中断。驱动代码可能很难编写，因为驱动与它所管理的设备并发执行。此外，驱动必须理解设备的接口（例如哪些 I/O 端口起什么作用），而该接口可能很复杂且文档匮乏。

磁盘驱动提供了一个很好的例子。磁盘驱动在磁盘与内存之间复制数据。磁盘硬件传统上把磁盘上的数据呈现为一系列编号的 512 字节块（也称为扇区）：扇区 0 是前 512 字节，扇区 1 是接下来的 512 字节，依此类推。操作系统为其文件系统使用的块大小可能与磁盘使用的扇区大小不同，但通常块大小是扇区大小的整数倍。xv6 的块大小与磁盘的扇区大小相同。xv6 用结构 struct buf 表示一个块。这个结构中存储的数据常常与磁盘不同步：它可能尚未从磁盘读入（磁盘正在处理，但还没有返回该扇区的内容），也可能已被更新但尚未写出。驱动必须确保当该结构与磁盘不同步时，xv6 的其余部分不会感到困惑。

代码：磁盘驱动 ​

IDE 设备提供对连接到 PC 标准 IDE 控制器的磁盘的访问。IDE 如今正被 SCSI 和 SATA 取代而逐渐过时，但它的接口简单，让我们能够专注于驱动的整体结构，而不是某块具体硬件的细节。

xv6 使用 struct buf 表示文件系统块。BSIZE (4068) 与 IDE 的扇区大小相同，因此每个缓冲区表示某个特定磁盘设备上一个扇区的内容。dev 和 sector 字段给出设备号和扇区号，data 字段是磁盘扇区在内存中的副本。尽管 xv6 文件系统选择让 BSIZE 与 IDE 的扇区大小相同，驱动也可以处理为扇区大小整数倍的 BSIZE。操作系统常常使用大于 512 字节的块以获得更高的磁盘吞吐量。

flags 跟踪内存与磁盘之间的关系：B_VALID 标志表示 data 已被读入，B_DIRTY 标志表示 data 需要写出。

内核在启动时由 main (1232) 调用 ideinit (4251) 来初始化磁盘驱动。Ideinit 调用 ioapicenable 启用 IDE_IRQ 中断 (4256)。对 ioapicenable 的调用只在最后一个 CPU（ncpu-1）上启用该中断：在双处理器系统上，CPU 1 处理磁盘中断。

接下来，ideinit 探测磁盘硬件。它首先调用 idewait (4257) 等待磁盘能够接受命令。PC 主板在 I/O 端口 0x1f7 上呈现磁盘硬件的状态位。Idewait (4238) 轮询状态位，直到忙位（IDE_BSY）清零且就绪位（IDE_DRDY）置位。

既然磁盘控制器已经就绪，ideinit 就可以检查有多少磁盘存在。它假定磁盘 0 存在，因为引导加载器和内核都是从磁盘 0 加载的，但它必须检查磁盘 1。它向 I/O 端口 0x1f6 写入以选择磁盘 1，然后等待一段时间，让状态位表明磁盘已就绪 (4259-4266)。如果不是，ideinit 就假定该磁盘不存在。

在 ideinit 之后，磁盘不再被使用，直到缓冲区缓存调用 iderw，后者按照标志所指示的方式更新一个已加锁的缓冲区。如果 B_DIRTY 被置位，iderw 就把缓冲区写到磁盘；如果 B_VALID 未置位，iderw 就从磁盘读取缓冲区。

磁盘访问通常需要几毫秒，对处理器来说是很长的时间。引导加载器发出磁盘读命令，并反复读取状态位直到数据就绪（见附录）。这种轮询或忙等待在引导加载器中是可以的，因为它没有更好的事情可做。然而在操作系统中，更高效的做法是让另一个进程在 CPU 上运行，并安排磁盘操作完成时接收一个中断。Iderw 采用后一种做法，把待处理的磁盘请求保存在一个队列中，并利用中断来了解每个请求何时完成。尽管 iderw 维护一个请求队列，简单的 IDE 磁盘控制器一次只能处理一个操作。磁盘驱动维护这样一个不变量：它已经把队列最前面的缓冲区发送给磁盘硬件；其余缓冲区只是在等待轮到自己。

Iderw (4354) 把缓冲区 b 加到队列末尾 (4367-4371)。如果该缓冲区位于队列最前面，iderw 就必须通过调用 idestart 把它发送给磁盘硬件 (4326-4328)；否则，等它前面的缓冲区处理完毕后，它就会被启动。

Idestart (4274) 根据标志为该缓冲区的设备和扇区发出读或写。如果操作是写，idestart 必须现在就提供数据 (4296)。idestart 使用 outsl 指令把数据移动到磁盘控制器中的缓冲区；用 CPU 指令在设备硬件之间移动数据称为程序控制 I/O。最终磁盘硬件会引发一个中断，表示数据已写入磁盘。如果操作是读，中断将表示数据已就绪，处理程序会读取它。注意，idestart 对 IDE 设备有详细的了解，并在正确的端口写入正确的值。如果这些 outb 语句中有任何一条写错，IDE 的行为就会与我们所期望的不同。把这些细节做对，是编写设备驱动具有挑战性的原因之一。

把请求加入队列并在必要时启动它之后，iderw 必须等待结果。如上所述，轮询不能高效利用 CPU。相反，iderw 通过睡眠把 CPU 让给其他进程，等待中断处理程序在缓冲区的标志中记录操作已完成 (4378-4379)。在这个进程睡眠期间，xv6 会调度其他进程，让 CPU 保持忙碌。

最终，磁盘会完成其操作并触发一个中断。trap 将调用 ideintr 来处理它 (3424)。Ideintr (4304) 查看队列中的第一个缓冲区，以弄清正在发生的是哪个操作。如果该缓冲区正在被读取，且磁盘控制器有数据在等待，ideintr 就用 insl 把数据从磁盘控制器中的缓冲区读入内存 (4317-4319)。现在缓冲区已就绪：ideintr 设置 B_VALID，清除 B_DIRTY，并唤醒在该缓冲区上睡眠的任何进程 (4321-4324)。最后，ideintr 必须把下一个等待的缓冲区传给磁盘 (4326-4328)。

现实世界 ​

要完整地支持 PC 主板上的所有设备是一项浩大的工作，因为设备很多、功能很多，而且设备与驱动之间的协议可能很复杂。在许多操作系统中，驱动加起来所占的代码量超过核心内核。

真实的设备驱动远比本章的磁盘驱动复杂，但基本思想是相同的：设备通常比 CPU 慢，因此硬件使用中断来通知操作系统状态变化。现代磁盘控制器通常一次接受一批磁盘请求，甚至会重新排序，以最高效地利用磁盘臂。在磁盘较简单的年代，操作系统常常自己重排请求队列。

许多操作系统都有固态盘的驱动，因为固态盘提供快得多的数据访问。但是，尽管固态盘的工作方式与传统机械磁盘非常不同，两种设备都提供基于块的接口，而且在固态盘上读写块仍然比读写 RAM 昂贵。

其他硬件与磁盘惊人地相似：网络设备的缓冲区存放数据包，音频设备的缓冲区存放声音采样，显卡的缓冲区存放视频数据和命令序列。高带宽设备——磁盘、显卡和网卡——常常使用直接内存访问（DMA）而不是程序控制 I/O（insl、outsl）。DMA 允许设备直接访问物理内存。驱动把缓冲区数据的物理地址交给设备，设备直接与主存之间复制，复制完成后产生一次中断。DMA 比程序控制 I/O 更快、更高效，对 CPU 的内存缓存负担也更小。

有些驱动会在轮询和中断之间动态切换，因为使用中断可能代价高昂，而使用轮询又可能引入延迟，直到驱动处理某个事件。例如，接收一串突发数据包的网络驱动可能从中断切换到轮询，因为它知道还有更多数据包必须处理，而用轮询处理它们代价更低。一旦不再需要处理数据包，驱动可能切回中断，以便在新数据包到达时立即得到通知。

IDE 驱动把中断静态地路由到某个特定处理器。有些驱动配置 IO APIC 把中断路由到多个处理器，以分散处理数据包的工作。例如，网络驱动可能安排把一个网络连接的数据包中断递送给管理该连接的那个处理器，而把另一个连接的数据包中断递送给另一个处理器。这种路由可以变得相当精细；例如，当某些网络连接是短时的而另一些是长时的，且操作系统希望让所有处理器都保持忙碌以实现高吞吐量时。

如果一个程序读取一个文件，该文件的数据会被复制两次。首先，驱动把它从磁盘复制到内核内存，然后 read 系统调用再把它从内核空间复制到用户空间。如果程序随后通过网络发送这些数据，数据又会被复制两次：从用户空间到内核空间，再从内核空间到网络设备。为了支持对效率要求很高的应用（例如在 Web 上提供热门图片），操作系统使用特殊的代码路径来避免复制。举例来说，在现实世界的操作系统中，缓冲区通常与硬件页大小一致，这样只读副本就可以用分页硬件映射到进程的地址空间，而无需任何复制。

练习 ​

  1. 在 syscall 的第一条指令处设置断点，以捕获第一次系统调用（例如 br syscall）。此时栈上有哪些值？解释该断点处 x/37x $esp 的输出，并标注每个值是什么（例如为 trap 保存的 %ebp、trapframe.eip、暂存空间等）。

  2. 添加一个新的系统调用，用于获取当前 UTC 时间并返回给用户程序。你可能想使用辅助函数 cmostime (7552) 来读取实时时钟。文件 date.h 包含 struct rtcdate 的定义，你将把它作为指针参数传给 cmostime。

  3. 为支持 SATA 标准的磁盘编写一个驱动（在 Web 上搜索 SATA）。与 IDE 不同，SATA 并未过时。使用 SATA 的标记命令队列向磁盘发出许多命令，使磁盘内部能够重排命令以获得高性能。

  4. 为以太网卡添加一个简单的驱动。
