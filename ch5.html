第 5 章　调度 ​

任何操作系统运行时，进程数量都很可能多于计算机的处理器数量，因此需要一套方案在进程之间对处理器分时。理想情况下，这种共享对用户进程应当是透明的。一种常见的做法是把进程多路复用到硬件处理器上，为每个进程提供一种幻觉：它拥有自己的虚拟处理器。本章解释 xv6 如何实现这种多路复用。

多路复用 ​

xv6 在两种情况下通过把每个处理器从一个进程切换到另一个进程来实现多路复用。第一，当进程等待设备或管道 I/O 完成、等待子进程退出，或者在 sleep 系统调用中等待时，xv6 的 sleep 与 wakeup 机制会进行切换。第二，当进程正在执行用户指令时，xv6 会定期强制切换。这种多路复用营造出每个进程都有自己的 CPU 的幻觉，正如 xv6 用内存分配器和硬件页表营造出每个进程都有自己的内存的幻觉一样。

实现多路复用带来几个挑战。第一，如何从一个进程切换到另一个进程？上下文切换的想法虽然简单，但其实现是 xv6 中最晦涩的代码之一。第二，如何透明地切换到用户进程？xv6 使用标准技术，用定时器中断驱动上下文切换。第三，许多 CPU 可能同时在进程之间切换，因此需要一套加锁方案来避免竞态。第四，进程退出时必须释放它的内存和其他资源，但进程自己无法完成全部清理，因为（举例来说）它不能在使用自己的内核栈的同时释放该栈。最后，多核机器的每个核都必须记住自己正在执行哪个进程，以便系统调用作用于正确进程的内核状态。xv6 试图尽可能简单地解决这些问题，但由此产生的代码仍然很棘手。

xv6 必须为进程提供彼此协调的方式。例如，父进程可能需要等待某个子进程退出，或者读管道的进程可能需要等待某个其他进程向管道写入。为了避免让等待的进程反复检查所期望的事件是否发生而浪费 CPU，xv6 允许进程放弃 CPU 并睡眠等待某个事件，同时允许另一个进程唤醒第一个进程。这里需要小心，避免出现导致事件通知丢失的竞态。作为这些问题及其解决方案的示例，本章考察管道的实现。

代码：上下文切换 ​

图 5-1 概述了从一个用户进程切换到另一个用户进程所涉及的步骤：从用户到内核的转换（系统调用或中断）进入旧进程的内核线程，上下文切换到当前 CPU 的调度器线程，再上下文切换到新进程的内核线程，最后陷阱返回到用户级进程。xv6 的调度器有自己的线程（保存的寄存器和栈），因为有时在某个进程的内核栈上执行它并不安全；我们将在 exit 中看到一个例子。本节考察在内核线程与调度器线程之间切换的机制。

从一个线程切换到另一个线程，涉及保存旧线程的 CPU 寄存器，并恢复新线程先前保存的寄存器；esp 和 eip 被保存和恢复，意味着 CPU 将切换栈，并切换它正在执行的代码。

函数 swtch 完成线程切换中的保存和恢复工作。swtch 并不直接了解线程；它只是保存和恢复寄存器组，这些寄存器组称为上下文。当某个进程该放弃 CPU 时，该进程的内核线程调用 swtch 保存自己的上下文，并返回到调度器上下文。每个上下文由一个 struct context* 表示，它是指向存放在相应内核栈上的结构的指针。Swtch 接受两个参数：struct context **old 和 struct context *new。它把当前寄存器压入栈，并把栈指针保存在 *old 中。然后 swtch 把 new 复制到 esp，弹出先前保存的寄存器，并返回。

我们跟随一个用户进程经过 swtch 进入调度器的过程。我们在 第 3 章 中看到，每次中断结束时的一种可能是 trap 调用 yield。Yield 又调用 sched，后者调用 swtch，把当前上下文保存在 proc->context 中，并切换到先前保存在 cpu->scheduler 中的调度器上下文 (2822)。

Swtch 首先把它的参数从栈复制到调用者保存寄存器 eax 和 edx；swtch 必须在改变栈指针、从而无法再通过 esp 访问参数之前完成这一步。然后 swtch 压入寄存器状态，在当前栈上构造一个上下文结构。只需要保存被调用者保存的寄存器；x86 的约定是这些寄存器为 ebp、ebx、esi、edi 和 esp。Swtch 显式压入前四个；它把最后一个隐含地保存为写入 *old 的 struct context*。还有一个重要的寄存器：程序计数器 eip。它已经由调用 swtch 的 call 指令保存在栈上。保存完旧上下文后，swtch 就准备好恢复新上下文。它把指向新上下文的指针移入栈指针。新栈的形式与 swtch 刚刚离开的旧栈相同——新栈在先前某次调用 swtch 时就是旧栈——因此 swtch 可以反向执行这一序列来恢复新上下文。它弹出 edi、esi、ebx 和 ebp 的值，然后返回。由于 swtch 已经改变了栈指针，被恢复的值和返回的指令地址都来自新上下文。

在我们的例子中，sched 调用 swtch 切换到 cpu->scheduler，即每 CPU 的调度器上下文。该上下文已由 scheduler 对 swtch 的调用保存。当我们一直追踪的这次 swtch 返回时，它返回到 scheduler 而不是 sched，并且它的栈指针指向当前 CPU 的调度器栈。

代码：调度 ​

上一节考察了 swtch 的底层细节；现在我们接受 swtch 作为既定条件，考察如何从一个进程经由调度器切换到另一个进程。想要放弃 CPU 的进程必须获取进程表锁 ptable.lock，释放它持有的其他所有锁，更新自己的状态（proc->state），然后调用 sched。Yield (2828) 遵循这一约定，我们稍后考察的 sleep 和 exit 也是如此。Sched 会复核这些条件，以及这些条件的一个推论：既然持有一把锁，CPU 就应当在关闭中断的情况下运行。最后，sched 调用 swtch，把当前上下文保存在 proc->context 中，并切换到 cpu->scheduler 中的调度器上下文。Swtch 在调度器的栈上返回，就好像 scheduler 的 swtch 返回了一样。调度器继续 for 循环，找到一个要运行的进程，切换到它，循环重复。

我们刚刚看到，xv6 在调用 swtch 期间一直持有 ptable.lock：swtch 的调用者必须已经持有该锁，而锁的控制权转移给被切换到的代码。这个约定对锁来说并不寻常；通常获取锁的线程也负责释放锁，这使正确性推理更容易。对于上下文切换，打破这个约定是必要的，因为 ptable.lock 保护进程 state 和 context 字段上的不变量，而这些不变量在 swtch 执行期间并不成立。如果在 swtch 期间不持有 ptable.lock，可能出现这样的问题：另一个 CPU 可能在 yield 已把进程状态设为 RUNNABLE 之后、但在 swtch 使其停止使用自己的内核栈之前，决定运行该进程。结果将是两个 CPU 在同一个栈上运行，这不可能正确。

内核线程总是在 sched 中放弃处理器，并且总是切换到调度器中的同一位置，而调度器（几乎）总是切换到先前调用过 sched 的某个内核线程。因此，如果把 xv6 切换线程处的行号打印出来，就会观察到下面这个简单的模式：(2781)、(2822)、(2781)、(2822)，依此类推。两个线程之间这种程式化切换所发生的那些过程，有时称为协程；在这个例子中，sched 和 scheduler 互为协程。

有一种情况下，调度器对 swtch 的调用最终不会进入 sched。我们在 第 2 章 中见过这种情况：新进程第一次被调度时，它从 forkret (2853) 开始。Forkret 的存在是为了释放 ptable.lock；否则，新进程可以直接从 trapret 开始。

Scheduler (2758) 运行一个简单的循环：找到一个要运行的进程，运行它直到它让出 CPU，然后重复。scheduler 在其大部分动作期间持有 ptable.lock，但在其外层循环的每次迭代中释放一次锁（并显式启用中断）。这对于当前 CPU 空闲（找不到 RUNNABLE 进程）的特殊情况很重要。如果空闲的调度器在一直持有锁的情况下循环，那么任何正在运行进程的其他 CPU 都永远无法执行上下文切换或任何与进程相关的系统调用，特别是永远无法把某个进程标记为 RUNNABLE，从而让空闲的 CPU 跳出调度循环。在空闲 CPU 上定期启用中断的原因是：可能没有 RUNNABLE 进程，因为进程（例如 shell）正在等待 I/O；如果调度器一直关闭中断，I/O 就永远不会到达。

调度器遍历进程表，寻找可运行的进程，即 p->state == RUNNABLE 的进程。一旦找到进程，它就设置每 CPU 的当前进程变量 proc，用 switchuvm 切换到该进程的页表，把该进程标记为 RUNNING，然后调用 swtch 开始运行它 (2774-2781)。

理解调度代码结构的一种方式是：它安排强制执行关于每个进程的一组不变量，并在这些不变量不成立时持有 ptable.lock。一个不变量是：如果进程处于 RUNNING，定时器中断的 yield 必须能够从该进程切换走；这意味着 CPU 寄存器必须保存该进程的寄存器值（即它们实际上并不在某个 context 中），cr3 必须指向该进程的页表，esp 必须指向该进程的内核栈，以便 swtch 能正确压入寄存器，并且 proc 必须指向该进程的 proc[] 槽位。另一个不变量是：如果进程处于 RUNNABLE，空闲 CPU 的 scheduler 必须能够运行它；这意味着 p->context 必须保存该进程的内核线程变量，没有 CPU 在该进程的内核栈上执行，没有 CPU 的 cr3 指向该进程的页表，也没有 CPU 的 proc 指向该进程。

维护上述不变量，正是 xv6 在一个线程中（通常是 yield）获取 ptable.lock、而在另一个线程（调度器线程或下一个内核线程）中释放该锁的原因。一旦代码开始修改运行中进程的状态以使其变为 RUNNABLE，它就必须持有该锁，直到它完成不变量的恢复：最早的正确释放点是在 scheduler 停止使用该进程的页表并清除 proc 之后。类似地，一旦 scheduler 开始把可运行的进程转换为 RUNNING，在对应的内核线程完全运行起来之前（swtch 之后，例如在 yield 中），都不能释放该锁。

ptable.lock 还保护其他东西：进程 ID 和空闲进程表槽位的分配、exit 与 wait 之间的相互作用、避免丢失唤醒的机制（见下一节），很可能还有别的东西。值得考虑是否可以拆分 ptable.lock 的不同职能，这当然有助于清晰性，也许还有助于性能。

代码：mycpu 与 myproc ​

xv6 为每个处理器维护一个 struct cpu，记录该处理器当前正在运行的进程（如果有）、处理器的唯一硬件标识（apicid）以及其他一些信息。函数 mycpu (2437) 返回当前处理器的 struct cpu。mycpu 的做法是从本地 APIC 硬件读取处理器标识，然后在 struct cpu 数组中查找具有该标识的项。mycpu 的返回值是脆弱的：如果定时器中断发生并导致线程被移到另一个处理器，返回值就不再正确。为了避免这个问题，xv6 要求 mycpu 的调用者禁用中断，并且只有在用完返回的 struct cpu 之后才重新启用中断。

函数 myproc (2457) 返回当前处理器上正在运行的进程的 struct proc 指针。myproc 禁用中断，调用 mycpu，从 struct cpu 中取出当前进程指针（c->proc），然后启用中断。如果没有进程在运行，因为调用者正在 scheduler 中执行，myproc 就返回零。myproc 的返回值即使在中启用了中断的情况下使用也是安全的：如果定时器中断把调用进程移到另一个处理器，它的 struct proc 指针仍保持不变。

睡眠与唤醒 ​

调度和锁帮助一个进程对另一个进程隐藏自己的存在，但到目前为止，我们还没有帮助进程有意交互的抽象。睡眠与唤醒填补了这一空白，允许一个进程睡眠等待某个事件，而另一个进程在该事件发生后唤醒它。睡眠与唤醒常常被称为顺序协调或条件同步机制，操作系统文献中还有许多其他类似的机制。

为了说明我们的意思，考虑一个简单的生产者/消费者队列。这个队列类似于把命令从进程送往 IDE 驱动的那个队列（见 第 3 章），但抽象掉了所有 IDE 特有的代码。该队列允许一个进程向另一个进程发送一个非零指针。如果只有一个发送者和一个接收者，它们在不同的 CPU 上执行，并且编译器没有做过于激进的优化，那么这个实现是正确的：

100101102103104105106107108109110111112113114115116117118119120121
struct q {
  void *ptr;
};

void*
send(struct q *q, void *p)
{
  while(q->ptr != 0)
    ;
  q->ptr = p;
}

void*
recv(struct q *q)
{
  void *p;

  while((p = q->ptr) == 0)
    ;
  q->ptr = 0;
  return p;
}

Send 循环直到队列为空（ptr == 0)，然后把指针 p 放入队列。Recv 循环直到队列非空，然后把指针取走。在不同进程中运行时，send 和 recv 都修改 q->ptr，但 send 只在指针为零时写入，recv 只在指针非零时写入，因此不会丢失更新。

上面的实现代价高昂。如果发送者很少发送，接收者将把大部分时间花在 while 循环中空转，期盼一个指针到来。接收者的 CPU 可以通过反复轮询 q->ptr 找到比忙等待更有成效的工作。避免忙等待需要一种办法，让接收者让出 CPU，并在 send 交付指针时才恢复。

我们来设想一对调用 sleep 和 wakeup，它们的工作方式如下。Sleep(chan) 在任意值 chan（称为等待通道）上睡眠。Sleep 使调用进程睡眠，把 CPU 让给其他工作。Wakeup(chan) 唤醒所有在 chan 上睡眠的进程（如果有），使它们的 sleep 调用返回。如果没有进程在 chan 上等待，wakeup 什么也不做。我们可以把队列实现改为使用 sleep 和 wakeup：

201202203204205206207208209210211212213214215216217218219
void*
send(struct q *q, void *p)
{
  while(q->ptr != 0)
    ;
  q->ptr = p;
  wakeup(q);  /* wake recv */
}

void*
recv(struct q *q)
{
  void *p;

  while((p = q->ptr) == 0)
    sleep(q);
  q->ptr = 0;
  return p;
}

Recv 现在放弃 CPU 而不是空转，这很好。然而事实证明，用这样的接口设计 sleep 和 wakeup 并不简单，会遭遇所谓的“丢失唤醒”问题（见 图 5-2）。假设 recv 在第 215 行发现 q->ptr == 0。当 recv 处于第 215 行和第 216 行之间时，send 在另一个 CPU 上运行：它把 q->ptr 改为非零，并调用 wakeup，而 wakeup 发现没有进程在睡眠，因此什么也不做。现在 recv 继续执行第 216 行：它调用 sleep 并进入睡眠。这造成一个问题：recv 正在睡眠，等待一个已经到达的指针。下一次 send 将等待 recv 消费队列中的指针，此时系统将死锁。

这个问题的根源在于，“recv 只在 q->ptr == 0 时才睡眠”这一不变量被恰好在错误时刻运行的 send 破坏了。一种不正确的保护不变量的做法是把 recv 的代码改成下面这样：

300301302303304305306307308309310311312313314315316317318319320321322323324325326327
struct q {
  struct spinlock lock;
  void *ptr;
};

void*
send(struct q *q, void *p)
{
  acquire(&q->lock);
  while(q->ptr != 0)
    ;
  q->ptr = p;
  wakeup(q);
  release(&q->lock);
}

void*
recv(struct q *q)
{
  void *p;

  acquire(&q->lock);
  while((p = q->ptr) == 0)
    sleep(q);
  q->ptr = 0;
  release(&q->lock);
  return p;
}

人们可能希望这个版本的 recv 能避免丢失唤醒，因为锁阻止了 send 在第 322 行和第 323 行之间执行。它确实做到了这一点，但它也会死锁：recv 在睡眠时持有锁，因此发送者将永远阻塞，等待该锁。

我们将通过改变 sleep 的接口来修正上述方案：调用者必须把锁传给 sleep，以便它在调用进程被标记为睡眠并在睡眠通道上等待之后释放该锁。这把锁将迫使并发的 send 等到接收者完成入睡，这样 wakeup 就能找到正在睡眠的接收者并唤醒它。一旦接收者再次醒来，sleep 会在返回前重新获取该锁。我们新的正确方案可以这样使用：

struct q {
  struct spinlock lock;
  void *ptr;
};

void*
send(struct q *q, void *p)
{
  acquire(&q->lock);
  while(q->ptr != 0)
    ;
  q->ptr = p;
  wakeup(q);
  release(&q->lock);
}

void*
recv(struct q *q)
{
  void *p;

  acquire(&q->lock);
  while((p = q->ptr) == 0)
    sleep(q, &q->lock);
  q->ptr = 0;
  release(&q->lock);
  return p;
}

recv 持有 q->lock 这一事实，阻止了 send 在 recv 检查 q->ptr 之后、调用 sleep 之前试图唤醒它。我们需要 sleep 原子地释放 q->lock 并让接收进程入睡。

一个完整的发送者/接收者实现，在 send 等待接收者消费上一次 send 的值时，也会在 send 中睡眠。

代码：睡眠与唤醒 ​

我们来看 sleep (2874) 和 wakeup (2953) 的实现。基本思想是让 sleep 把当前进程标记为 SLEEPING，然后调用 sched 释放处理器；wakeup 查找在给定等待通道上睡眠的进程，并把它标记为 RUNNABLE。sleep 和 wakeup 的调用者可以使用任何对双方都方便的数值作为通道。xv6 常常使用参与等待的某个内核数据结构的地址。

Sleep (2874) 以几项健全性检查开始：必须存在当前进程 (2878)，并且必须向 sleep 传入了一把锁。然后 sleep 获取 ptable.lock (2891)。现在，将要睡眠的进程同时持有 ptable.lock 和 lk。在调用者中（在例子中是 recv）持有 lk 是必要的：它确保没有其他进程（在例子中是运行 send 的进程）能够开始调用 wakeup(chan)。既然 sleep 持有 ptable.lock，释放 lk 就是安全的：某个其他进程可能开始调用 wakeup(chan)，但 wakeup 要等到能获取 ptable.lock 才会运行，因此它必须等到 sleep 完成让进程入睡，从而避免 wakeup 错过这次 sleep。

有一个小麻烦：如果 lk 等于 &ptable.lock，那么 sleep 会死锁——它试图以 &ptable.lock 的身份获取它，然后又以 lk 的身份释放它。在这种情况下，sleep 认为获取和释放相互抵消，于是完全跳过它们 (2890)。例如，wait 就以 &ptable.lock 调用 sleep。

既然 sleep 持有 ptable.lock 而不持有其他锁，它就可以通过记录睡眠通道、改变进程状态并调用 sched 来让进程入睡 (2895-2898)。

在此后的某个时刻，某个进程会调用 wakeup(chan)。Wakeup 获取 ptable.lock 并调用 wakeup1，后者做实际工作。wakeup 持有 ptable.lock 很重要，一方面是因为它在操作进程状态，另一方面正如我们刚刚看到的，ptable.lock 确保 sleep 和 wakeup 不会彼此错过。Wakeup1 是一个单独的函数，因为有时调度器需要在已经持有 ptable.lock 的情况下执行唤醒；我们稍后会看到一个例子。Wakeup1 (2953) 遍历进程表。当它找到状态为 SLEEPING 且 chan 匹配的进程时，就把该进程的状态改为 RUNNABLE。调度器下次运行时，就会看到该进程已可运行。

xv6 代码总是在持有守护睡眠条件的锁时调用 wakeup；在上面的例子中，那把锁是 q->lock。严格说来，只要 wakeup 总是在 acquire 之后调用就够了（也就是说，可以在 release 之后调用 wakeup）。为什么 sleep 和 wakeup 的加锁规则能确保睡眠的进程不会错过它需要的唤醒？睡眠进程从检查条件之前的某个点，到被标记为睡眠之后的某个点，要么持有条件锁，要么持有 ptable.lock，要么两者都持有。如果某个并发线程使条件变为真，该线程要么在睡眠线程获取条件锁之前持有它，要么在睡眠线程于 sleep 中释放它之后持有它。如果是前者，睡眠线程必定已经看到了新的条件值，却仍然决定睡眠，因此即使错过唤醒也无所谓。如果是后者，那么唤醒者最早只能在 sleep 获取 ptable.lock 之后获取条件锁，因此 wakeup 对 ptable.lock 的获取必须等到 sleep 完全完成让睡眠者入睡。这样 wakeup 就会看到正在睡眠的进程并唤醒它（除非有别的什么东西先把它唤醒）。

有时多个进程会在同一个通道上睡眠；例如，多个进程从同一个管道读取。一次 wakeup 调用会把它们全部唤醒。其中一个会先运行，获取调用 sleep 时传入的锁，并（在管道的情形中）读取管道中等待的数据。其他进程会发现，尽管被唤醒，却没有数据可读。从它们的角度看，这次唤醒是“虚假的”，它们必须再次睡眠。由于这个原因，sleep 总是在检查条件的循环内部调用。

如果两处使用 sleep/wakeup 的地方碰巧选择了相同的通道，也不会造成损害：它们会看到虚假唤醒，但如上所述的循环能够容忍这个问题。sleep/wakeup 的魅力在很大程度上在于它既轻量（无需创建特殊的数据结构来充当睡眠通道），又提供了一层间接性（调用者无需知道自己正在与哪个具体进程交互）。

代码：管道 ​

我们本章前面使用的简单队列只是个玩具，但 xv6 包含两个真正的队列，它们使用 sleep 和 wakeup 来同步读者和写者。一个在 IDE 驱动中：进程把磁盘请求加入队列，然后调用 sleep。IDE 中断处理程序使用 wakeup 通知该进程它的请求已完成。

一个更复杂的例子是管道的实现。我们在 第 0 章 中看到了管道的接口：写入管道一端的字节被复制到内核内的缓冲区，然后可以从管道的另一端读出。后续各章将考察管道周围的文件描述符支持，但现在我们先看 pipewrite 和 piperead 的实现。

每个管道由一个 struct pipe 表示，其中包含一个 lock 和一个 data 缓冲区。字段 nread 和 nwrite 统计从缓冲区读出和写入的字节数。缓冲区是环绕的：在 buf[PIPESIZE-1] 之后写入的下一个字节是 buf[0]。计数值不环绕。这个约定使实现能够区分满缓冲区（nwrite == nread+PIPESIZE）和空缓冲区（nwrite == nread），但它意味着对缓冲区的索引必须使用 buf[nread % PIPESIZE] 而不是仅仅 buf[nread]（对 nwrite 也是如此）。我们假设对 piperead 和 pipewrite 的调用在两个不同的 CPU 上同时发生。

Pipewrite (6830) 首先获取管道的锁，它保护计数值、数据以及相关的不变量。Piperead (6851) 随后也试图获取该锁，但获取不到。它在 acquire (1580) 中自旋等待该锁。在 piperead 等待期间，pipewrite 遍历要写入的字节——addr[0]、addr[1]、……、addr[n-1]——把它们依次加入管道。在这个循环中，可能出现缓冲区被填满的情况 (6836)。此时，pipewrite 调用 wakeup 通知任何睡眠的读者缓冲区中有数据在等待，然后在 &p->nwrite 上睡眠，等待读者从缓冲区取走一些字节。Sleep 在让 pipewrite 的进程入睡的过程中释放 p->lock。

既然 p->lock 已经可用，piperead 成功获取它并进入自己的临界区：它发现 p->nread != p->nwrite (6856)（pipewrite 之所以去睡眠，是因为 p->nwrite == p->nread+PIPESIZE (6836)），于是它进入 for 循环，从管道中复制数据 (6863-6867)，并按复制的字节数增加 nread。现在有这么多字节可供写入，因此 piperead 在返回调用者之前调用 wakeup (6868)，唤醒任何睡眠的写者。Wakeup 找到一个在 &p->nwrite 上睡眠的进程，即先前运行 pipewrite 但在缓冲区填满时停下的那个进程。它把该进程标记为 RUNNABLE。

管道代码为读者和写者使用不同的睡眠通道（p->nread 和 p->nwrite）；在大量读者和写者等待同一管道这种不太可能的情况下，这可能使系统更高效。管道代码在检查睡眠条件的循环内部睡眠；如果有多个读者或写者，除第一个醒来的进程外，其他进程都会发现条件仍为假，于是再次睡眠。

代码：wait、exit 与 kill ​

Sleep 和 wakeup 可用于多种等待。一个有趣的例子（见 第 0 章）是父进程用来等待子进程退出的 wait 系统调用。子进程退出时并不会立即消亡。相反，它切换到 ZOMBIE 进程状态，直到父进程调用 wait 得知其退出。父进程随后负责释放与该进程关联的内存，并把 struct proc 准备好以供重用。如果父进程先于子进程退出，init 进程会收养该子进程并等待它，从而使每个子进程都有父进程为其善后。

实现上的一个挑战是父子的 wait 与 exit 之间，以及 exit 与 exit 之间可能发生竞态。Wait 首先获取 ptable.lock。然后它扫描进程表寻找子进程。如果 wait 发现当前进程有子进程但都没有退出，它就调用 sleep 等待其中一个退出 (2707)，然后再次扫描。这里，在 sleep 中被释放的锁是 ptable.lock，也就是我们上面看到的特殊情况。

Exit 获取 ptable.lock，然后唤醒任何在等于当前进程父进程 proc 的等待通道上睡眠的进程；如果有这样的进程，它就是处于 wait 中的父进程。这看起来可能为时过早，因为 exit 还没有把当前进程标记为 ZOMBIE，但这是安全的：尽管 wakeup 可能使父进程运行，但 wait 中的循环要等到 exit 通过调用 sched 进入调度器而释放 ptable.lock 之后才能运行，因此 wait 在 exit 把其状态设为 ZOMBIE 之前无法查看正在退出的进程 (2663)。在 exit 让出处理器之前，它会把正在退出的进程的所有子进程重新指定父进程，交给 initproc。最后，exit 调用 sched 放弃 CPU。

如果父进程正睡眠在 wait 中，调度器最终会运行它。对 sleep 的调用在返回时持有 ptable.lock；wait 重新扫描进程表，找到 state == ZOMBIE 的已退出子进程 (2657)。它记录子进程的 pid，然后清理 struct proc，释放与该进程关联的内存 (2687-2694)。

子进程本可以在 exit 期间完成大部分清理，但重要的是让父进程来释放 p->kstack 和 p->pgdir：当子进程运行 exit 时，它的栈位于作为 p->kstack 分配的内存中，并且它使用自己的页表。只有在子进程通过调用 swtch（经由 sched）完成最后一次运行之后，才能释放它们。这是调度器过程运行在自己的栈上、而不是运行在调用 sched 的线程的栈上的原因之一。

exit 允许进程终止自己，而 kill (2975) 允许一个进程请求终止另一个进程。让 kill 直接销毁受害进程会过于复杂，因为受害者可能在另一个 CPU 上执行，或者在更新内核数据结构的中途睡眠。为了应对这些挑战，kill 做得很少：它只设置受害者的 p->killed，如果受害者正在睡眠，就唤醒它。最终受害者会进入或离开内核，此时如果 p->killed 已置位，trap 中的代码就会调用 exit。如果受害者正在用户空间运行，它很快就会通过发起系统调用、或者因为定时器（或其他设备）中断而进入内核。

如果受害进程正处于 sleep，对 wakeup 的调用将使受害进程从 sleep 返回。这有潜在危险，因为它所等待的条件可能并不成立。然而，xv6 对 sleep 的调用总是包裹在一个 while 循环中，在 sleep 返回后重新检查条件。有些 sleep 调用还在循环中检查 p->killed，如果已置位就放弃当前活动。只有在这样放弃是正确的场合才会这样做。例如，管道读写代码 (6837) 在 killed 标志置位时返回；最终代码会返回 trap，trap 会再次检查该标志并退出。

有些 xv6 的 sleep 循环不检查 p->killed，因为代码正处于一个应当原子完成的多步系统调用中间。IDE 驱动 (4379) 就是一个例子：它不检查 p->killed，因为一次磁盘操作可能是使文件系统保持正确状态所需的一组写操作之一。为了避免部分操作之后清理工作的复杂性，xv6 会推迟杀死处于 IDE 驱动中的进程，直到稍后某个容易杀死该进程的时刻（例如，当完整的文件系统操作已完成、进程即将返回用户空间时）。

现实世界 ​

xv6 调度器实现一种简单的调度策略，依次运行每个进程。这种策略称为轮转。真实操作系统实现更精细的策略，例如允许进程拥有优先级。其想法是，调度器会偏好可运行的高优先级进程而非可运行的低优先级进程。这些策略可能很快变得复杂，因为常常存在相互竞争的目标：例如，操作系统可能还想保证公平性和高吞吐量。此外，复杂策略可能导致意料之外的相互作用，例如优先级反转和护航效应。当低优先级进程和高优先级进程共享一把锁，而该锁被低优先级进程获取后可能阻止高优先级进程取得进展时，就会发生优先级反转。当许多高优先级进程等待某个获取了共享锁的低优先级进程时，就可能形成长长的护航队列；一旦形成，护航可能持续很长时间。为了避免这类问题，精细的调度器需要额外的机制。

Sleep 和 wakeup 是一种简单有效的同步方法，但还有许多其他方法。它们共同的首要挑战是避免我们在本章开头看到的“丢失唤醒”问题。原始 Unix 内核的 sleep 只是禁用中断，这就足够了，因为 Unix 运行在单 CPU 系统上。由于 xv6 运行在多处理器上，它给 sleep 增加了一把显式的锁。FreeBSD 的 msleep 采用同样的做法。Plan 9 的 sleep 使用一个回调函数，该函数在即将睡眠之前、持有调度锁的情况下运行；这个函数充当对睡眠条件的最后检查，以避免丢失唤醒。Linux 内核的 sleep 使用显式的进程队列而不是等待通道；该队列有自己的内部锁。

在 wakeup 中扫描整个进程列表以寻找 chan 匹配的进程是低效的。更好的办法是把 sleep 和 wakeup 中的 chan 替换为一种数据结构，其中保存着在该结构上睡眠的进程列表。Plan 9 的 sleep 和 wakeup 把这种结构称为会合点或 Rendez。许多线程库把同样的结构称为条件变量；在那个语境中，sleep 和 wakeup 这两个操作被称为 wait 和 signal。所有这些机制都有相同的特点：睡眠条件由某种锁保护，而该锁在睡眠期间被原子地释放。

wakeup 的实现会唤醒所有在某个特定通道上等待的进程，而可能有许多进程正在等待那个特定通道。操作系统将调度所有这些进程，它们会竞相检查睡眠条件。以这种方式行事的进程有时称为惊群，最好避免。大多数条件变量为 wakeup 提供两个原语：signal 唤醒一个进程，broadcast 唤醒所有等待的进程。

信号量是另一种常见的协调机制。信号量是一个整数值，有两个操作：递增和递减（或 up 和 down）。递增信号量总是可行的，但信号量的值不允许降到零以下：对值为零的信号量递减会睡眠，直到另一个进程递增该信号量，然后这两个操作相互抵消。这个整数值通常对应一个真实的计数，例如管道缓冲区中可用的字节数，或进程拥有的僵尸子进程数。把显式计数作为抽象的一部分，可以避免“丢失唤醒”问题：存在一个已发生唤醒次数的显式计数。这个计数还避免了虚假唤醒和惊群问题。

终止进程并清理它们给 xv6 带来了许多复杂性。在大多数操作系统中，这还要复杂得多，因为举例来说，受害进程可能正深陷内核之中睡眠，展开它的栈需要非常谨慎的编程。许多操作系统使用显式的异常处理机制（例如 longjmp）来展开栈。此外，还有其他事件可能导致睡眠的进程被唤醒，即使它所等待的事件尚未发生。例如，当一个 Unix 进程正在睡眠时，另一个进程可能向它发送一个 signal。在这种情况下，该进程将从被中断的系统调用返回，返回值为 -1，错误码被设为 EINTR。应用程序可以检查这些值并决定怎么做。xv6 不支持信号，因此不会出现这种复杂性。

xv6 对 kill 的支持并不完全令人满意：有些 sleep 循环大概应当检查 p->killed。一个相关的问题是，即使对于那些检查 p->killed 的 sleep 循环，sleep 与 kill 之间也存在竞态；后者可能在受害者的循环检查完 p->killed 之后、但在它调用 sleep 之前，设置 p->killed 并试图唤醒受害者。如果发生这个问题，受害者要等到它所等待的条件出现时才会注意到 p->killed。这可能要等很久（例如，当 IDE 驱动返回受害者正在等待的磁盘块时），或者永远等不到（例如，如果受害者正在等待来自控制台的输入，而用户没有输入任何内容）。

练习 ​

  1. Sleep 必须检查 lk!= &ptable.lock 以避免死锁 (2890-2893)。假设通过把
if(lk != &ptable.lock){
  acquire(&ptable.lock);
  release(lk);
}

替换为

release(lk);
acquire(&ptable.lock);

来消除这个特殊情况。这样做会破坏 sleep。怎么破坏的？

  1. 大部分进程清理工作本可以由 exit 或 wait 完成，但我们上面看到 exit 不能释放 p->stack。事实证明，必须由 exit 来关闭打开的文件。为什么？答案与管道有关。

  2. 在 xv6 中实现信号量。你可以使用互斥锁，但不要使用 sleep 和 wakeup。用信号量替换 xv6 中对 sleep 和 wakeup 的使用。评价结果。

  3. 修复上面提到的 kill 与 sleep 之间的竞态，使得在受害者的 sleep 循环检查完 p->killed 之后、调用 sleep 之前发生的 kill，会导致受害者放弃当前系统调用。

  4. 设计一个方案，让每个 sleep 循环都检查 p->killed，从而使例如处于 IDE 驱动中的进程在另一个进程杀死它时能够迅速从 while 循环返回。

  5. 设计一个方案，在从一个用户进程切换到另一个用户进程时只使用一次上下文切换。这个方案涉及在用户进程的内核栈上运行调度器过程，而不是在专用的调度器栈上。主要挑战是正确地清理用户进程。测量避免一次上下文切换所带来的性能收益。

  6. 修改 xv6，使处理器在空闲、只是在 scheduler 的循环中空转时关闭。（提示：查看 x86 的 HLT 指令。）

  7. 锁 p->lock 保护许多不变量，当查看 xv6 中受 p->lock 保护的某段代码时，很难弄清正在强制执行的是哪个不变量。设计一个更清晰的方案，也许把 p->lock 拆成几把锁。
